Issue #98 is the local-data-transport half split from the stronger
presence/ranging gate.

Its source scope is:

  * mDNS peer discovery over local Wi-Fi;
  * LAN TCP/QUIC transport through mini-bearer;
  * Wi-Fi Direct where supported;
  * store-and-forward integration with bootstrap/sync.

Its hard rule is:

  connectivity and physical-proximity evidence are different problems.

This report makes the security consequence explicit:

  WI-FI NETWORK CONTEXT CONTRIBUTES ZERO PERSONHOOD,
  ZERO HUMAN-UNIQUENESS,
  ZERO PHYSICAL-PRESENCE,
  ZERO HUMAN-CONTINUITY NETWORK-CONTEXT SCORE.

Wi-Fi may TRANSPORT a protected device-key continuity challenge.

The cryptographic key response may be continuity evidence under the independent
continuity design.

The fact that the bytes traversed:
  same SSID;
  same BSSID;
  same router;
  same subnet;
  same hotspot;
  low-latency LAN;
  Wi-Fi Direct;
  Wi-Fi Aware;
  VPN/tunnel;
  public Wi-Fi
contributes zero evidence.

This supersedes the old gate document's implication that Wi-Fi co-networking
might itself feed the "device/home continuity" score.

The current human-continuity design gives the safer rule already:
device/home continuity is a protected key answering unpredictable challenges
over separated epochs and explicitly excludes IP address, Wi-Fi name, street
address and similar raw network/location identifiers.

Why zero is the only durable rule:

  * VPNs can extend private subnets;
  * mDNS reflectors can cross VLANs/sites;
  * hotspots can host Sybil farms;
  * public Wi-Fi joins unrelated strangers;
  * enterprise WLANs span large areas;
  * MAC addresses randomize/spoof;
  * SSID/BSSID are mutable/spoofable;
  * local proxies can represent remote peers;
  * latency is not distance;
  * routers are infrastructure, not humans.

No future convenience feature may silently reopen this boundary.

3. EXTERNAL STANDARDS / PLATFORM RESEARCH
========================================================================

R98-01 — RFC 6762 mDNS

RFC 6762 is the actual standards-track Multicast DNS protocol.

Relevant wire facts:
  UDP port 5353;
  IPv4 224.0.0.251;
  IPv6 FF02::FB;
  DNS message semantics;
  local-link operation without conventional DNS infrastructure.

Decision:
  production infrastructure-LAN discovery uses actual RFC6762 semantics through
  platform APIs.

R98-02 — RFC 6763 DNS-SD

DNS-SD discovers service instances using standard DNS records:
  PTR;
  SRV;
  TXT.

Decision:
  Mininet uses a DNS-SD TCP service profile.

Proposed type:
  `_mininet._tcp`

Before public interoperability release:
  verify/register the service name with IANA as appropriate.

IANA is namespace coordination only.

Runtime local discovery must never require reaching IANA.

R98-03 — Android NsdManager

Android documents NsdManager as DNS-SD over mDNS.

Current API guidance favors asynchronous tracking of found/updated/lost
services and warns that resolved addresses can become stale.

Decision:
  Android infrastructure LAN uses NsdManager.

R98-04 — Android multicast power model

Android documents that raw Wi-Fi multicast may be filtered and that acquiring a
MulticastLock can cause noticeable battery drain.

Decision:
  no permanent raw multicast lock on an ordinary phone.

R98-05 — Android 17 local-network permission

For target API37+, Android requires local-network permission for broad LAN
advertise/connect workflows, with system-mediated scoped alternatives for some
service discovery flows.

Decision:
  permission denial is a supported normal state.

It cannot:
  revoke identity;
  reduce personhood;
  freeze funds;
  remove governance rights.

R98-06 — Android nearby Wi-Fi permission

Modern Wi-Fi Direct/Aware APIs require `NEARBY_WIFI_DEVICES` in applicable
versions.

Decision:
  request only when the user invokes/enables that functionality.

Never request/use Wi-Fi data to infer human physical location for Gate #98.

R98-07 — Android Wi-Fi Direct

Android supports peer-to-peer Wi-Fi without Internet and supports service
discovery.

Decision:
  optional Android direct bearer.

Not a universal requirement.

R98-08 — Wi-Fi Aware/NAN

Wi-Fi Aware is a Wi-Fi Alliance peer-to-peer standard for discovery and data
communication without an AP or Internet.

Android supports it.

Apple introduced Wi-Fi Aware support in iOS 26 and documents it on compatible
modern devices.

Decision:
  preferred long-term standards-based cross-platform direct-Wi-Fi substrate
  where both endpoints support it.

R98-09 — Apple Multipeer Connectivity

Apple marks Multipeer Connectivity deprecated and directs developers to
Network.framework.

Decision:
  no new Mininet core dependence on Multipeer Connectivity.

R98-10 — Apple Network.framework

Use Network.framework/Bonjour for future iOS LAN networking.

R98-11 — TCP vs QUIC

Issue #98 allowed TCP/QUIC.

Mininet already has TCP.

Apple's current TN3213 says Wi-Fi Aware + QUIC is not supported prior to iOS 27
and aligned releases.

Decision:
  TCP is V1.

QUIC may be additive later after cross-platform evidence.

R98-12 — Apple local-network privacy

Future iOS support must declare truthful local-network usage and Bonjour service
types.

Permission denial is normal.

No Apple account becomes a Mininet prerequisite.

========================================================================
10. STORE-AND-FORWARD INTEGRATION
========================================================================

Wi-Fi is live contact.

When both peers are online:

  discover -> connect -> Channel -> app authenticate -> exchange inventory ->
  transfer missing immutable objects.

When the path disappears:

  unsent content stays in app/sync/deferred durable state.

Do not turn TcpBearer into persistent mail.

Later Wi-Fi contact may drain:
  private messages;
  public objects;
  CRDT ops;
  KEL events;
  storage chunks;
  forge objects;
  signed transaction/payment submissions;
  governance submissions.

Transport delivery is never:
  payment finality;
  governance count;
  personhood;
  physical presence.

Application semantic ID deduplicates repeated delivery.
