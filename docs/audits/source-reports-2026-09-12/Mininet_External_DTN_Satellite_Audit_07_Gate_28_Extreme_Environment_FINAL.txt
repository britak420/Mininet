======================================================================
0. EXECUTIVE ANSWER
======================================================================

YES — RFC 9171 Bundle Protocol Version 7 fits Mininet's architecture.

It fits unusually well because Mininet already has:

  * immutable content-addressed objects;
  * opaque encrypted private object envelopes;
  * local-first application state;
  * a direct bearer abstraction;
  * a strict split between pending local payment claims and canonical finality.

The architecture should NOT turn `mini_bearer::Bearer` into a magical link that
blocks for six months.

Instead, add a separate asynchronous `mini-dtn` store-carry-forward layer above
the object/operation layer and alongside the live bearer/session layer.

The central design decision is:

  LIVE TRANSPORT and DEFERRED TRANSPORT are different semantics.

Live:
  send/recv;
  duplex;
  session;
  ordered cryptographic channel;
  useful for Internet/BLE/Wi-Fi contacts that currently exist.

Deferred:
  enqueue immutable object/operation;
  persist;
  carry;
  forward during future contact;
  deliver at least once;
  reorder/duplicate freely;
  no end-to-end session assumed.

RFC 9171 BPv7 is the V1 interoperability wire protocol for the deferred path.

Mininet implements its own narrow Rust BPv7 profile and uses NASA ION/HDTN or
other standards-compliant BPv7 nodes as INTEROPERABILITY TEST PEERS, not as
runtime authorities and not as required hosted services.

No local region is ever allowed to finalize the SAME global MINI ledger while
cut off and later "merge" money.

That idea is rejected.

Content and CRDT application state may merge.

Global MINI ownership, global constitutional governance execution, and global
monetary parameters do not merge.

A disconnected region may:
  communicate;
  create signed objects;
  create queued transactions;
  receive locally accepted payment promises;
  coordinate locally;
  maintain content;
  prepare votes/proposals;
  carry canonical proofs it already has.

It may not claim:
  new global monetary finality;
  global governance finality;
  canonical treasury authority
without the globally valid chain state required by those operations.

That single rule removes the most dangerous ambiguity in the previous gate
document.

1. CURRENT SOURCE VERDICT
======================================================================

D7-F01 — PASS
Current `mini-settlement` already has the correct finality split.

Mechanism:
  `SettlementState` contains:
    SignedLocal
    AcceptedLocal
    PendingCanonical
    Finalized
    RejectedConflict
    RejectedCanonical
    Expired

Only:
  Finalized
returns:
  is_final() == true.

This is exactly the right basis for disruption-tolerant money.

D7-F02 — PASS
Canonical ordering alone decides conflicting spends.

Location:
  `crates/mini-settlement/src/reconcile.rs`

Mechanism:
  `reconcile()` can return Finalized only from a `CanonicalLedgerView`.

A local relay:
  cannot finalize.

A hotspot:
  cannot finalize.

A partition committee:
  cannot finalize.

A DTN gateway:
  cannot finalize.

Preserve this.

D7-F03 — PARTIAL
Current `PaymentClaim` is signed and bounded but its expiry semantics are
Internet/device-clock shaped.

Location:
  `crates/mini-settlement/src/claim.rs`

Current fields include:
  `valid_until_ms`
and the source describes it as:
  device-clock milliseconds.

Local acceptance and reconciliation compare caller `now_ms` against it.

Exact failure:
  a wall/device clock is not a robust canonical validity boundary for a claim
  that may spend days or months in a disconnected store-carry-forward network.

Decision:
  PaymentClaimV2 uses canonical chain anchoring and canonical economic-epoch
  expiry, Section 15.

D7-F04 — PASS AS LIVE BEARER / FAIL AS DTN API
Current `mini_bearer::Bearer` is correctly documented as:
  frame-oriented;
  best-effort;
  live send/recv.

Its own documentation says:
  delay-tolerant users must add retransmission/reordering above it.

That is a good boundary.

Do NOT distort the trait to make a live bearer impersonate persistent mail.

D7-F05 — FAIL FOR ASYNCHRONOUS E2E SESSION USE
Current `mini_bearer::Channel` performs a two-message live handshake and uses
monotonic in-order AEAD counters.

That is correct for an active connection.

It is not the end-to-end security format for an object that may be:
  stored for 30 days;
  copied through 12 relays;
  delivered after both original sessions disappeared.

Decision:
  DTN transports independently verifiable Mininet object/operation bytes.
  Live Channel may secure a current contact, but it is never required to decrypt
  the stored object at the final destination.

D7-F06 — PASS / STRONG FIT
Current `mini-objects::ObjectEnvelopeV2` already provides an excellent private
DTN payload substrate.

Mechanism:
  outer envelope contains only:
    version;
    AEAD suite;
    opaque routing tag;
    coarse retention class;
    nonce;
    ciphertext.

The content ID covers canonical outer bytes.

Tampering is detectable.

The relay need not decrypt.

Exact residual:
  the envelope itself does not hide:
    source IP;
    timing;
    ciphertext length;
    repeated route access.

DTN therefore still needs routing-metadata privacy policy.

D7-F07 — PASS / STRONG FIT
Current unified object model has:
  signed immutable objects;
  content IDs;
  sequence/timestamp;
  typed links.

Current `MAX_PAYLOAD_BYTES` is:
  8 MiB.

For DTN V1:
  the global object cap may remain 8 MiB;
  the deferred-transport profile uses a stricter 1 MiB bundle payload ceiling
  and requires large data to use storage-fabric chunks/manifests.

D7-F08 — PASS / STRONG FIT
`mini-messaging` already stores private messages as opaque V2 object envelopes.

It explicitly does not claim key establishment is solved by the storage layer.

That is the correct security layering.

For DTN:
  a stored private message envelope can be carried unchanged.

D7-F09 — PASS
SPEC-04 already says large content is chunked into a Merkle DAG and each chunk
is content-verifiable.

That directly solves the application-level segmentation problem better than
asking BP to fragment huge encrypted application objects.

D7-F10 — PASS
SPEC-09 already declares:
  signed immutable objects;
  CRDT collaborative state;
  offline-first reconciliation.

Those objects are natural DTN ADUs.

D7-F11 — FAIL / ABSENT
No `mini-dtn` crate exists in the reviewed main crate set.

No BPv7:
  parser;
  serializer;
  persistent bundle queue;
  convergence layer;
  contact plan;
  bundle age;
  hop-count;
  ION interoperability harness
was found in current main.

This is an implementation absence, not a design failure.

D7-F12 — PARTIAL
The existing gate draft sketches:

  `DelayTolerantTransport::custody_transfer()`

as if custody transfer were a basic BPv7 requirement.

That is no longer the right V1 abstraction.

RFC 9171 does not make old BP custody-transfer semantics part of its core
service.

CCSDS published a separate experimental custody-transfer specification in 2026.

Decision:
  remove mandatory custody transfer from the base Mininet DTN interface.
  Optional custody capability is an extension only.

======================================================================

This section states what Mininet itself requires before outside DTN research is
applied.

2.1 SPEC-03

The connectivity specification defines Mininet as:
  a true network of networks.

Its frozen direction requires:
  key/self-certifying addressing;
  bearer swappability;
  content-blind relay;
  local-first operation;
  continued function inside mesh range when wider Internet is cut.

It explicitly says:
  off-grid transactions queue and finalize on reconnection.

That is the governing monetary constraint for this report.

2.2 SPEC-04

Storage is:
  content-addressed;
  tamper-evident;
  chunked for large objects;
  blind/encrypted when desired;
  weak-device friendly.

A DTN relay should therefore carry:
  existing Mininet bytes
rather than inventing a second content system.

2.3 SPEC-09

Application state is built from:
  signed immutable objects;
  signed pointers;
  CRDT operation logs;
  local views.

It explicitly describes app state as:
  offline-first.

This report preserves CRDT reconciliation for content/social/code state.

It does NOT extend CRDT merge semantics into canonical money.

2.4 Constitution / sovereignty

Mininet cannot force a user to replicate their data.

DTN store-and-forward is therefore:
  opt-in for locally authored private data;
  subject to application retention policy;
  never a protocol power to seize/copy plaintext.

A user may choose:
  device-only.

They accept:
  no delayed delivery while device remains unreachable.

2.5 Later project direction

The current project has removed LoRa/radio as a required Mininet platform
dependency.

This report therefore does NOT reintroduce:
  RNode;
  LoRa;
  packet radio
as mandatory components.

BPv7 remains bearer-neutral and can use any future permitted link.

Near-term Mininet DTN work uses:
  IP;
  BLE/local mesh contacts;
  Wi-Fi;
  ordinary satellite IP;
  standards-compatible space links through adapters.


======================================================================
3. EXTERNAL STANDARDS RESEARCH — DECISIONS
======================================================================

3.1 RFC 9171 BPv7

RFC 9171 is the IETF Standards Track Bundle Protocol Version 7.

It is specifically designed for:
  intermittent connectivity;
  long/variable delay;
  high loss;
  store-carry-forward operation.

It supplies:
  Endpoint Identifiers;
  creation timestamps;
  bundle lifetimes;
  Bundle Age extension;
  Hop Count extension;
  forwarding/deletion semantics;
  optional fragmentation;
  application delivery status.

DECISION:
  BPv7 is Mininet's DTN interoperability protocol.

Do not invent:
  "MINI Bundle Protocol."

3.2 Bundle Age

RFC 9171 provides Bundle Age specifically for nodes without accurate clocks.

DECISION:
  every Mininet DTN bundle created with a zero DTN creation time MUST carry
  Bundle Age per RFC 9171.

Mininet relay expiration must be able to operate without:
  NTP;
  GPS;
  cellular clock;
  centralized time server.

3.3 Hop count

BPv7 allows a hop limit in the range 1..255.

Mininet profile:

  normal/disaster default: 32
  scheduled/deep-space default: 64
  Mininet-generated maximum: 64

A receiving interoperable BP node may still accept standards-compliant bundles
with a larger limit subject to local policy.

Why Mininet caps its own:
  route loops must not become infinite storage/bandwidth debt.

3.4 Lifetime

BPv7 nodes may impose a shorter effective local lifetime if a bundle threatens
local resources.

DECISION:
  transport retention is a best-effort network resource promise.

It is NOT:
  application ownership;
  money validity;
  governance deadline;
  global content deletion.

A relay may delete its local copy and the protocol remains correct.

3.5 RFC 9172 BPSec

BPSec provides:
  integrity;
  confidentiality
for Bundle Protocol blocks.

It explicitly assumes:
  untrusted DTN paths;
  stored data;
  no guaranteed regular access to a centralized certificate/security oracle.

This aligns with Mininet's anti-centralization values.

DECISION:
  a native Mininet BP agent MUST implement the BPSec processing model before it
  advertises BPSec support.

However:
  Mininet private application data remains independently end-to-end encrypted
  at the Mininet object/message layer.

BPsec is additional bundle-layer protection.

It is not allowed to become:
  the only reason a stored private Mininet message is confidential.

3.6 RFC 9173 default BPSec contexts

RFC 9173 specifies:
  BIB-HMAC-SHA2;
  BCB-AES-GCM.

DECISION:
  support these for interoperability when BPSec is enabled.

Do not make their symmetric key distribution:
  a central CA;
  a hosted Mininet key server;
  a universal network root.

BPSec peer/endpoint policy may use:
  locally provisioned keys;
  pairwise capabilities;
  mission-specific keys
at the DTN edge.

Mininet object's own author/recipient trust remains did:mini/object-layer trust.

3.7 RFC 9174 TCPCLv4

TCPCLv4 is the standardized reliable TCP convergence layer for BPv7.

DECISION:
  TCPCLv4 is REQUIRED for Mininet's first native IP DTN interoperability
  profile.

This gives a stable test target.

It does not mean:
  every BLE contact is tunnelled through TCP.

Convergence layers remain pluggable.

3.8 LTP

RFC 5326 Licklider Transmission Protocol is designed for:
  extremely long RTT;
  frequent interruption;
  retransmission-based reliability.

It is not an IETF Standards Track Internet transport.

It is nevertheless established DTN/space prior art and CCSDS has standardized
its space profile separately.

DECISION:
  Mininet does NOT reimplement LTP in the first DTN milestone.

For actual long-delay scheduled space-link interoperability:
  support an LTP-capable external BP peer/gateway during testing;
  later a Rust LTP adapter may be added if Mininet must directly terminate the
  link.

The Mininet core does not depend on LTP.

3.9 Raw UDP BP

RFC 7122 discourages direct BP-over-datagram use in ordinary IP networks because
BP itself does not provide the retransmission/congestion-control behavior needed
there.

DECISION:
  raw UDP BP is NOT the default Mininet DTN convergence layer.

Use:
  TCPCLv4 for ordinary IP;
  a fit-for-link reliable convergence layer for stressed links.

3.10 CCSDS SABR

CCSDS 734.3-B-1 Schedule-Aware Bundle Routing uses known future contact plans for
scheduled space communications.

DECISION:
  scheduled satellite/lunar/Mars deployments MAY use SABR/CGR-compatible
  routing.

But:
  a contact plan is routing advice.

It is never:
  identity authority;
  authorization;
  payment finality;
  governance legitimacy.

No NASA/operator contact-plan server is required by Mininet.

3.11 CCSDS BPv7 status

As of this report:
  CCSDS 734.20-O-1 (April 2025) is an EXPERIMENTAL BPv7 specification based on
  RFC 9171.

The older CCSDS 734.2-B-1 Blue Book is based on RFC 5050/BPv6.

DECISION:
  RFC 9171 is the Mininet normative BPv7 baseline.

Do not claim:
  the old BPv6 Blue Book is a BPv7 authority.

3.12 CCSDS custody transfer status

As of June 2026:
  CCSDS 734.6-O-1 is an Orange Book experimental specification for Custody
  Transfer and Compressed Bundle Status Reporting.

DECISION:
  custody transfer is OPTIONAL / EXPERIMENTAL in Mininet.

No correctness property may depend on a relay promising custody.

3.13 Current IETF work in 2026

The DTN WG/working ecosystem currently includes:
  reliability guidance;
  BTP-U for unidirectional unreliable frame links;
  a new QUIC convergence-layer draft;
  renewed BIBE work.

These are still Internet-Drafts / work in progress where not published as RFCs.

DECISION:
  design adapters for them.

Do not make V1 correctness depend on a draft.

3.14 BTP-U

The 2026 BTP-U draft is directly relevant to:
  unidirectional;
  unreliable;
  frame-based;
  non-IP links;
  no-return-path operation.

DECISION:
  experimental feature only until the standards status is suitable.

This is exactly the kind of future satellite adapter Mininet should be able to
add without changing its application semantics.

3.15 QUICCL

The July 2026 QUICCL draft maps BPv7 onto:
  QUIC streams;
  QUIC datagrams;
  multiple delivery modes;
  priorities.

DECISION:
  experimental adapter.

TCPCLv4 remains the V1 required IP interop target because it is already an RFC.

3.16 BIBE

Current 2026 BIBE work focuses on bundle-in-bundle encapsulation and optional
segmentation.

DECISION:
  keep a future BIBE tunnel adapter seam.

Do not require it for V1.

3.17 Operational evidence

NASA states that its DTN project completed in January 2026 and DTN is now an
operational service in both:
  Near Space Network;
  Deep Space Network.

NASA reports PACE has transmitted more than 34 million bundles with a 100%
reported success rate to date.

This does NOT prove Mininet implementation correctness.

It does prove:
  DTN/BPv7 is not merely a hypothetical Mars paper architecture in 2026.

3.18 ION / HDTN / DTNME

NASA publishes/points to multiple DTN implementations including:
  ION;
  HDTN;
  DTNME;
  BPv7 cFS components.

DECISION:
  use at least two independent BPv7 implementations as interoperability peers
  where practical.

They are test counterparts.

Mininet does NOT require:
  NASA infrastructure;
  a NASA account;
  one vendor daemon;
  one hosted BP gateway.

4. FINAL SCOPE DECISION
======================================================================

D28-01 — FOUR REGIMES ARE ARCHITECTURALLY IN SCOPE.

R0 — ordinary connected transport
  Existing live bearer path.
  DTN not normally selected.

R1 — disaster / opportunistic terrestrial partition
  Minutes to days without end-to-end path.
  Unscheduled peer contacts.
  Primary near-term DTN implementation target.

R2 — scheduled satellite / near-space / lunar
  Seconds-scale propagation plus scheduled outage/contact windows.
  BPv7 + standards-compatible scheduled routing.
  Second implementation target.

R3 — deep-space / Mars / interplanetary
  minutes to hours one-way;
  long no-contact periods;
  severe asymmetry.

Architecture and emulation:
  in scope now.

Actual mission integration:
  not a terrestrial launch gate.

D28-02 — LEO INTERNET IS NOT AUTOMATICALLY "DTN MODE."

A continuous Starlink-class or other satellite Internet path is simply:
  an Internet bearer
when it behaves like one.

Do not impose BP store-carry-forward overhead merely because photons touched a
satellite.

DTN activates because of:
  disruption;
  intermittent contact;
  long delay;
  asymmetry;
  store-carry requirement,
not a vendor label.

D28-03 — DISASTER MODE IS THE FIRST REAL IMPLEMENTATION TARGET.

Reason:
  it immediately strengthens the founding local-first promise and is testable
  without owning a spacecraft.

D28-04 — DEEP-SPACE COMPATIBILITY IS AN ARCHITECTURAL TEST, NOT A SYNCHRONOUS
CONSENSUS PROJECT.

No:
  "Mars CometBFT round-trip mode";
  "planet-wide synchronous ceremony";
  "global session that waits 44 minutes per message."

Applications enqueue immutable operations and proofs.

The canonical chain continues wherever its required validator network can
communicate.

A remote region learns/submits state asynchronously.

D28-05 — NO SAME-ASSET LOCAL CANONICAL ZONES.

The prior gate draft called local settlement zones a likely future answer.

This audit rejects that for canonical MINI.

Reason:
  two disconnected zones that both finalize spends from the same global
  ownership namespace create exactly the state-merge/double-spend ambiguity
  `mini-settlement` correctly avoids.

If humanity eventually wants independent planetary currencies/chains:
  they are independent ledgers connected through explicit bridge/finality rules.

They are NOT:
  invisible local forks of the same MINI state that magically merge later.

D28-06 — LOCAL ECONOMIC FUNCTION REMAINS POSSIBLE.

Allowed:
  signed PaymentClaim;
  local bilateral risk acceptance;
  payment/channel protocols whose security model explicitly permits offline use;
  local barter/credit outside canonical MINI;
  queued canonical transactions.

UI must say:
  Pending
or:
  Accepted locally — not final.

Never:
  Final
until canonical chain proves it.

D28-07 — CONTENT/SOCIAL/CODE STATE MAY MERGE.

CRDT-safe application state:
  comments;
  issue operations;
  messages;
  collaborative document operations
can merge under their own signed-object semantics.

Canonical value:
  does not CRDT-merge.

Canonical governance execution:
  does not CRDT-merge.

D28-08 — DTN GATE #28 IS NON-BLOCKING FOR TERRESTRIAL MAINNET.

The design gate exists to prevent architecture that fails catastrophically under
long delay.

It is not a requirement that Earth mainnet have a live Mars relay before value
exists.

On adoption of this report:
  #28 may close.

Future implementation is tracked as an implementation milestone, not an
unresolved domain-research gate.

D28-10 — BASE API IS ASYNCHRONOUS.

Conceptual interface:

  pub trait DeferredTransport {
      fn enqueue(
          &mut self,
          parcel: DeferredParcel
      ) -> Result<DeferredId, DtnError>;

      fn poll_delivered(
          &mut self,
          limit: usize
      ) -> Result<Vec<DeliveredParcel>, DtnError>;

      fn status(
          &self,
          id: &DeferredId
      ) -> Result<DeferredStatus, DtnError>;

      fn cancel_local(
          &mut self,
          id: &DeferredId
      ) -> Result<(), DtnError>;
  }

No mandatory:
  `custody_transfer()`.

D28-11 — DELIVERY SEMANTICS ARE AT-LEAST-ONCE.

A bundle may be:
  duplicated;
  retransmitted;
  received more than once;
  arrive out of order.

Every application payload type must be:
  content-addressed;
  sequence-aware;
  transaction-ID/nullifier-aware;
  otherwise idempotent.

Exactly-once transport is NOT promised.

D28-12 — DELIVERY RECEIPT IS NOT APPLICATION FINALITY.

RFC 9171's delivery status means:
  payload reached the application agent.

It does not mean:
  the application processed it successfully.

Mininet maps states explicitly:

  QueuedLocal
  StoredLocal
  Forwarded
  BundleDelivered
  ObjectAccepted
  SubmittedCanonical
  IncludedCanonical
  FinalizedCanonical
  ExpiredTransport
  RejectedApplication

For money:
  only FinalizedCanonical is monetary finality.

D28-13 — THE BP AGENT IS NOT A TRUST ROOT.

Even if the local BP queue process is compromised, the app must verify:
  content ID;
  object signature/provenance;
  transaction signature;
  chain proof;
  nullifier;
  policy
as appropriate.

A BP daemon may:
  drop;
  delay;
  duplicate;
  reorder.

It may not forge a valid Mininet object merely by returning bytes.

6. MININET DTN PAYLOAD PROFILE
======================================================================

D28-14 — TRANSPORT MININET OBJECT/OPERATION BYTES, NOT LIVE SESSION STATE.

Eligible:

  public signed object;
  ObjectEnvelopeV2;
  private message object envelope;
  CRDT operation;
  KEL / identity event;
  block header / finality proof;
  canonical transaction submission;
  PaymentClaimV2;
  storage/content chunk;
  storage manifest;
  forge object;
  governance proposal/vote object subject to canonical deadline.

Not eligible as deferred semantic truth:

  live presence-ranging exchange;
  active BLE RTT;
  live Noise/X25519 Channel handshake transcript;
  ephemeral TCP/QUIC stream state;
  "local finality";
  a relay's opinion that payment is settled.

D28-15 — CONTENT ADDRESS IS THE APPLICATION DEDUP KEY.

Bundle ID:
  transport identity.

Object ID / transaction ID:
  application semantic identity.

Two bundles carrying the same Mininet object:
  may have different BP bundle IDs.

Application stores/processes the object once.

D28-16 — PRIVATE PAYLOADS REMAIN OPAQUE TO DTN RELAYS.

For existing private object/message path:
  carry `ObjectEnvelopeV2::to_bytes()` unchanged.

Do not decrypt and re-encrypt at every DTN relay.

No gateway:
  needs conversation key.

D28-17 — PUBLIC OBJECTS REMAIN SELF-VERIFYING.

A public signed object does not need to become secret merely because BP carries
it.

On receipt:
  verify object ID;
  verify object signature/provenance if the application relies on authorship.

D28-18 — DTN DOES NOT SOLVE KEY DISTRIBUTION.

The current messaging source correctly says an authenticated conversation key
must already exist.

A delayed transport adapter must not introduce:
  a central prekey directory
merely because messages are asynchronous.

Key establishment remains the messaging/identity security lane.


======================================================================
7. SIZE / CHUNKING / FRAGMENTATION DECISION
======================================================================

D28-19 — MININET V1 DOES NOT RELY ON BP REACTIVE FRAGMENTATION.

BPv7 supports fragmentation.

Mininet deliberately does not use it for normal security-bearing Mininet V1
payloads.

Reason:

  * application objects already have integrity/content identity;
  * storage fabric already has chunked Merkle DAGs;
  * retransmitting one huge fragment tree increases resource-abuse complexity;
  * BPSec and fragmentation have additional processing complexity;
  * small independently verifiable chunks fit intermittent contacts better.

D28-20 — 1 MiB MAXIMUM MININET DTN APPLICATION PAYLOAD.

  MAX_DTN_PAYLOAD_BYTES = 1_048_576

This is stricter than:
  mini-objects MAX_PAYLOAD_BYTES = 8 MiB.

It does NOT reduce the global object limit.

It means:
  an object larger than the DTN profile must be represented through a manifest /
  chunked storage structure for deferred transport.

D28-21 — CONTROL / MONEY / GOVERNANCE OBJECT MAXIMUM 64 KiB.

  MAX_DTN_CONTROL_PAYLOAD_BYTES = 65_536

Includes:
  payment claim;
  vote;
  proposal action;
  KEL update;
  finality proof envelope where format permits.

If a proof is inherently larger:
  it uses a signed manifest/chunk form instead of increasing an unbounded
  "critical packet" class.

D28-22 — MESSAGE BODY STAYS AT CURRENT 64 KiB LIMIT.

Attachments:
  content-addressed separately.

Do not put:
  2 GiB video
inside an urgent chat bundle.

D28-23 — WHY 1 MiB.

At 8 kbit/s, ignoring overhead:

  64 KiB requires approximately 65.5 seconds.

  1 MiB requires approximately 17.5 minutes.

  8 MiB requires approximately 2.33 hours.

A 1 MiB upper payload limit makes a single interrupted transfer survivable on
very low-rate links while still being efficient on terrestrial contacts.

D28-24 — PRE-CHUNK BEFORE SIGNING THE MANIFEST.

Large data:
  chunk first;
  hash each chunk;
  build signed/content-addressed manifest;
  transport chunks independently.

The receiver never accepts a partial giant application object as complete.

D28-25 — INTEROPERABILITY FRAGMENTS MAY BE RECEIVED SAFELY.

A standards-compliant external BP node may send a fragmented BPv7 bundle.

A Mininet BP parser:
  may support reassembly for interoperability
only under:
  strict byte quota;
  fragment-count quota;
  lifetime;
  authenticated/integrity policy.

Mininet does not SOURCE fragments in V1.

Hard local reassembly limits:

  <= 1 MiB assembled Mininet payload
  <= 64 fragments
  <= local queue quota

Anything larger:
  reject for the Mininet DTN service.

8. TRANSPORT LIFETIME / AGE DECISION
======================================================================

D28-26 — TRANSPORT EXPIRY AND APPLICATION VALIDITY ARE SEPARATE.

Never compare:

  BP bundle lifetime
with:
  canonical payment validity
as if they were the same rule.

Bundle lifetime:
  how long relays should try carrying these bytes.

Payment validity:
  whether canonical chain can still include the signed claim.

Governance deadline:
  whether canonical governance epoch can still accept the vote.

Object retention:
  how long storage participants choose to seed an object.

Four different semantics.

D28-27 — MININET BUNDLE LIFETIME CLASSES.

  Ephemeral:
    1 hour

  Short:
    24 hours

  Standard:
    30 days

  Archival:
    180 days

  DeepSpace:
    365 days

The source application selects from these bounded classes.

No arbitrary:
  "retain forever."

D28-28 — LOCAL RELAYS MAY SHORTEN THEIR EFFECTIVE RETENTION.

This follows RFC 9171's resource-protection model.

A weak phone is not obligated to sacrifice all disk because another node put
"365 days" in a bundle.

Deletion by one relay:
  is not global deletion.

D28-29 — ZERO-CLOCK MODE USES BUNDLE AGE.

A node without trustworthy wall time:
  creation time may be zero as permitted by BPv7;
  Bundle Age becomes mandatory.

No NTP server:
  is a correctness authority.

D28-30 — TRANSPORT EXPIRY NEVER UN-FINALIZES MONEY.

If a bundle containing a transaction expires at one relay after the transaction
already became canonical elsewhere:
  the transaction stays canonical.

Likewise:
  a finalized transaction remains final after all transport copies disappear.


======================================================================
9. PRIORITY / FAIRNESS DECISION
======================================================================

D28-31 — PRIORITY IS FUNCTIONAL, NEVER PURCHASED.

No:
  MINI balance;
  fee size;
  founder status;
  institutional role;
  hardware capacity
changes DTN scheduling class.

D28-32 — FOUR LOCAL QUEUE CLASSES.

P0 — protocol-critical bounded control
  finality/header safety proofs;
  identity key-revocation events where structurally valid;
  narrowly defined safety/control objects.

P1 — human-control / canonical-submission
  governance vote/proposal submissions;
  canonical transaction submissions;
  PaymentClaim delivery;
  small identity continuity objects.

P2 — interactive
  direct messages;
  CRDT ops;
  ordinary small posts;
  emergency coordination messages.

P3 — bulk
  content chunks;
  repository history;
  archival synchronization;
  non-urgent storage replication.

D28-33 — USER CANNOT SELF-LABEL ARBITRARY BYTES P0.

P0 qualification comes from:
  parseable object type;
  valid signature/proof where cheap;
  size <=64 KiB;
  local admission policy.

An unknown blob claiming:
  "EMERGENCY!!!"
does not get unlimited critical priority.

D28-34 — WORK-CONSERVING DEFICIT ROUND ROBIN.

When all queues are non-empty, scheduling weights:

  P0: 4
  P1: 3
  P2: 2
  P3: 1

Nominal shares under continuous contention:

  P0 40%
  P1 30%
  P2 20%
  P3 10%

Unused share:
  is immediately borrowable by other non-empty queues.

No reserved bandwidth sits idle.

D28-35 — PRIORITY DOES NOT CHANGE APPLICATION LEGITIMACY.

A P0 bundle does not:
  gain a vote;
  gain finality;
  become trusted;
  bypass signature checks.

It only gets earlier forwarding opportunity.

D28-36 — BULK CANNOT STARVE FOREVER.

Under continuous valid P0/P1/P2 load:
  P3 still receives its DRR share.

This prevents an administrative/control class from turning into a permanent
content censor.


======================================================================
10. STORAGE / RESOURCE-EXHAUSTION DECISION
======================================================================

D28-37 — RELAY STORAGE IS VOLUNTARY AND BOUNDED.

Default mobile DTN relay:
  OFF until user enables relay/store-carry participation.

Receiving bundles addressed to the local user:
  remains possible when DTN is enabled.

Default opt-in mobile relay disk budget:

  min(
    512 MiB,
    10% of currently available free local storage
  )

with a minimum operational floor:
  if configured budget <64 MiB,
  transit relaying stays disabled.

Node/server operators may configure larger budgets.

D28-38 — PRESERVE USER SPACE.

Hard free-space floor:
  do not allocate new transit bundles if doing so would leave less than:
    max(1 GiB, 5% filesystem capacity)
  free.

Locally authored/user-addressed application storage is governed separately.

D28-39 — GLOBAL QUEUE IS BOUNDED.

No:
  Vec of unlimited bundles;
  unbounded fragment table;
  unbounded status-report queue.

Every table has:
  byte limit;
  entry limit;
  expiry/GC.

D28-40 — UNTRUSTED SOURCE ADMISSION IS GLOBAL + PER-NEIGHBOR.

Suggested V1 default on mobile relay:

  one currently connected untrusted neighbor may contribute at most:
    16 MiB
  of uncommitted new transit data during one encounter
  before application-level/peer policy grants more.

Global new-untrusted ingress token bucket:
  4 MiB/minute
  burst 16 MiB
on mobile.

Operators may raise these.

They may not configure:
  an unbounded allocation.

D28-41 — DEDUP BEFORE DURABLE SECOND COPY WHERE POSSIBLE.

Check:
  bundle ID;
  Mininet application object/transaction ID
before spending storage on duplicate payload.

A duplicate may refresh:
  route knowledge
but does not need another full application blob.

D28-42 — VALIDATE CHEAPLY BEFORE EXPENSIVE WORK.

Order:

  framing / length
  BP structural parse
  bundle age/lifetime
  hop count
  duplicate ID
  service EID
  cheap content ID / envelope bounds
  then expensive signatures/BPSec/application proof.

DoS attacker does not get free expensive cryptography before basic bounds.

D28-43 — STATUS REPORTS OFF BY DEFAULT.

Reasons:
  extra traffic;
  metadata leakage;
  reflection/amplification surface.

Enable:
  only per application/diagnostic policy.

A delivery status report never counts as money finality.

11. ROUTING DECISION
======================================================================

D28-44 — ROUTING POLICY IS LOCAL, NOT CONSENSUS.

Two honest nodes may choose different:
  next hops;
  contact plans;
  queue strategies
and still agree on Mininet application truth.

Routing does not enter:
  chain consensus.

D28-45 — DIRECT DELIVERY FIRST.

If destination is currently reachable:
  forward directly unless user privacy tier requires a different path.

DTN is not an excuse to add unnecessary hops.

D28-46 — OPPORTUNISTIC TERRESTRIAL BASELINE: BOUNDED SPRAY-AND-WAIT.

For networks without a contact schedule:

  P0:
    initial copy budget 4

  P1:
    initial copy budget 4

  P2:
    initial copy budget 4

  P3:
    initial copy budget 2

Copy budget is transport metadata/local routing state.

It does not modify application payload.

When only one forwarding copy remains:
  wait for destination or a clearly better local route.

This prevents:
  full epidemic replication.

A deployment may use a better open routing algorithm without changing the wire
truth.

D28-47 — SCHEDULED SPACE BASELINE: SABR/CGR-COMPATIBLE ROUTING.

For known contacts:
  use contact plan:
    start;
    end;
    sender;
    receiver;
    expected rate;
    one-way range
to compute earliest feasible forwarding opportunities.

D28-48 — CONTACT PLANS ARE ADVISORY.

A malicious plan can:
  waste bandwidth;
  cause delay;
  route into dead ends.

It cannot:
  sign an object;
  finalize money;
  authorize governance;
  revoke identity.

D28-49 — NO SINGLE CONTACT-PLAN PUBLISHER.

Accept plans from:
  local operator;
  peer;
  mission source;
  multiple configured feeds.

The operator decides which schedules to use.

No Mininet-global:
  "official satellite timetable server."

D28-50 — ROUTE CHURN MUST NOT REWRITE OBJECT ID.

Changing:
  next hop;
  scheduled link;
  convergence layer
does not alter the Mininet application object.

The same bytes can travel through a different path.

12. ENDPOINT NAMING / CENTRALIZATION DECISION
======================================================================

D28-51 — BP EID IS NOT DID:MINI IDENTITY.

Never set a private user's public BP endpoint to:
  their stable root did:mini
by default.

That would create:
  cross-path metadata linkage.

D28-52 — PRIVATE MININET ENDPOINTS USE OPAQUE / ROTATABLE DTN ROUTE EIDS.

The DTN service maintains:
  an opaque route capability / EID mapping.

The peer learns it through:
  an authenticated Mininet relationship;
  a signed capability object;
  another already-secure path.

It is not a global legal-name directory.

D28-53 — IPN URI IS AN INTEROPERABILITY EDGE, NOT THE HUMAN NAMESPACE.

RFC 9758's public `ipn` allocator structure involves allocator identifiers and
registries.

That is acceptable for:
  spacecraft;
  public gateway;
  mission node interoperability.

It is NOT acceptable as:
  Mininet human identity authority.

For private/non-interoperable tests:
  use the RFC-defined private-use ranges where appropriate.

For Mininet-native private people:
  prefer opaque dtn-scheme endpoint capabilities.

D28-54 — ROUTING ID NEVER CREATES GOVERNANCE STANDING.

An operator owning:
  a registered IPN allocator;
  a satellite gateway;
  a public DTN EID
gets zero extra Mininet vote weight.

13. CONVERGENCE LAYER PROFILE

D28-55 — TCPCLV4 REQUIRED FOR V1 IP INTEROP.

Test:
  Mininet Rust BP agent <-> at least two independent compatible BPv7 peers.

D28-56 — LIVE BEARER CONTACT ADAPTER IS ALLOWED.

For BLE/local Wi-Fi encounters:
  an already-established Mininet live bearer can be used as a convergence

D28-57 — LTP IS OPTIONAL FOR ACTUAL SPACE LINK TERMINATION.

If a Mininet node sits behind an ION/HDTN gateway:
  the gateway may terminate LTP.

Mininet application payload remains self-verifying.

Feature flag:
  experimental-quiccl

No:
  consensus;

depends on it.

D28-59 — BTP-U IS EXPERIMENTAL UNTIL STANDARDIZED.

Feature flag:
  experimental-btpu

Potential use:
  future one-way satellite/frame links.

D28-60 — RAW UDP BP IS NOT DEFAULT.

Any experimental UDP deployment must:
  define its reliability/congestion behavior
and:
  stay within the relevant standards/security constraints.

14. SECURITY MODEL
======================================================================

D28-61 — TWO SECURITY LAYERS, DIFFERENT JOBS.

Application security:
  Mininet object ID/signature/AEAD/capability.

Bundle security:
  BPSec where configured.

Live contact security:
  `mini-bearer::Channel` or convergence-layer TLS/peer protection.

Do not collapse them.

D28-62 — APPLICATION SECURITY SURVIVES AN UNTRUSTED GATEWAY.

A satellite operator can store bytes.

It cannot:
  read ObjectEnvelopeV2 payload;
  forge signed public object;
  change payment amount;
  change vote
without application verification failing.

D28-63 — NO CENTRAL CERTIFICATE AUTHORITY BECOMES MININET ROOT.

TCPCL TLS may use:
  deployment-local certificates;
  pinned peer keys;
  normal PKI
as transport hardening.

Failure of that CA:
  may break that convergence path.

It may not invalidate:
  did:mini;
  existing Mininet objects;
  canonical chain.

D28-64 — AT-REST PRIVATE CONTENT REMAINS CIPHERTEXT.

A transit node should not need application decryption key merely to:
  queue;
  carry;
  forward.

D28-65 — METADATA PRIVACY IS NOT OVERCLAIMED.

BP primary routing information can expose:
  endpoint identifiers;
  timing;
  size;
  contact relationships.

ObjectEnvelopeV2 hides application semantics.

It does NOT make BP traffic metadata invisible.

D28-66 — STATUS/DIAGNOSTIC MINIMIZATION.

Production default:
  no unnecessary BP status reports;
  no raw EID logs longer than local debugging retention;
  no central telemetry upload required.

D28-67 — ONION/MIX AND DTN ARE COMPOSABLE BUT NOT IDENTICAL.

A BP gateway may be one transport hop inside a broader privacy route.

Do not promise:
  the standard BP header itself is a Sphinx packet.

Sensitive asynchronous application payload can use:
  opaque endpoint capabilities;
  application encryption;
  future BIBE/tunnel/mix composition.

D28-68 — ROUTING PRIVACY NEVER REQUIRES DECRYPTING CONTENT.

A router needs:
  transport metadata.

It does not need:
  message body;
  payment memo;
  human legal identity.

15. PAYMENTCLAIMV2 — FINAL LONG-DELAY MONEY DECISION
======================================================================

The existing PaymentClaim is close to the correct model but wall-clock expiry is
wrong for canonical long-delay semantics.

D28-69 — ADD PAYMENTCLAIMV2.

Conceptual structure:

  struct ChainAnchorV2 {
      height: u64,
      block_id: [u8; 32],
      economic_epoch: u64,
  }

  struct PaymentClaimV2 {
      version: u8,
      network_id: [u8; 32],
      payer: PublicKey,
      payee_commitment: Vec<u8>,
      amount: Amount,
      sequence: u64,
      anchor: ChainAnchorV2,
      valid_through_economic_epoch: u64,
      claim_context: [u8; 32],
      signature: Signature,
  }

D28-70 — CANONICAL EXPIRY USES CANONICAL ECONOMIC EPOCH.

Gate #6 already defines:
  twelve deterministic Economic Epochs per Economic Year.

Claim is eligible for canonical inclusion only if:

  current_canonical_economic_epoch
    <= valid_through_economic_epoch

and:
  the anchor block is a recognized ancestor of the canonical chain state
  required by the payment executor.

No recipient wall clock decides global ownership.

D28-71 — HARD MAX CLAIM LIFETIME: TWELVE ECONOMIC EPOCHS.

  1 <=
    valid_through_economic_epoch - anchor.economic_epoch
  <= 12

Maximum:
  one Economic Year.

Recipient may demand:
  a much shorter window.

Reason:
  no indefinitely reusable signed spend promise;
  enough room for prolonged disaster/deep-space carriage;
  deterministic chain-time boundary.

D28-72 — V1 `valid_until_ms` BECOMES LEGACY / UI-ONLY FOR NEW DTN PROFILE.

Do not reinterpret old signed bytes.

PaymentClaimV1 remains:
  versioned historical/test compatibility.

New real-value delayed settlement:
  PaymentClaimV2.

D28-73 — ANCHOR AGE IS RISK INFORMATION.

A claim anchored to very old state may still be structurally valid within its
epoch window.

Recipient UI must expose:

  anchor height/epoch;
  last canonical proof age;
  local acceptance amount threshold;
  unresolved prior claim count if known.

Old anchor:
  never magically becomes safe because a relay signed custody.

D28-74 — LOCAL ACCEPTANCE REMAINS RECIPIENT RISK.

The current `LocalAcceptancePolicy::never_accept_early()` remains the
conservative default.

For real value:
  default remains:
    0 early acceptance

until the user explicitly chooses a nonzero local-risk limit.

No UI may describe AcceptedLocal as:
  "settled."

D28-75 — CANONICAL CONFLICT RULE UNCHANGED.

Same payer + same sequence + different claim:

  canonical chain chooses at most one.

DTN duplicate copies:
  do not create multiple payment rights.

D28-76 — BP DELIVERY DOES NOT CONSUME A PAYMENT SLOT.

Only application/canonical processing does.

A relay receipt cannot:
  spend;
  reserve;
  finalize
payer funds by itself.

D28-77 — TRANSPORT TTL MAY BE SHORTER THAN CLAIM VALIDITY.

That is allowed.

Example:
  claim valid for six economic epochs;
  one relay chooses 24h local retention;
  bundle expires there.

Another route/copy may still deliver it.

D28-78 — CLAIM EXPIRY MAY BE SHORTER THAN BUNDLE TTL.

On receipt:
  application sees canonical claim expired;
  rejects it
even if BP bundle itself is still within lifetime.

D28-79 — NO OFFLINE TREASURY EXECUTION.

Treasury:
  contribution mint;
  monetary-parameter change;
  bridge supply change
requires its normal canonical/threshold/finality policy.

A DTN queue may carry the request/signature.

It cannot relax the policy.

16. CHAIN / LIGHT-CLIENT OPERATION OVER DTN
======================================================================

D28-80 — TRANSPORT FINALITY PROOFS AS IMMUTABLE OBJECTS.

A remote node should be able to receive:

  finalized header/checkpoint;
  validator/committee proof;
  relevant state proof;
  block/object chunks

through BP.

It verifies them locally.

The DTN gateway is not trusted for their truth.

D28-81 — NO LIVE RPC REQUIREMENT FOR VERIFICATION.

If a light-client proof bundle contains all required data:
  verification works without querying a central API.

D28-82 — STATE SYNC IS CONTENT-ADDRESSED.

Large:
  block bodies;
  snapshots;
  application content
are chunked and content-addressed.

Contacts carry:
  missing chunks.

D28-83 — REMOTE NODE CAN BE STALE WITHOUT BECOMING A FORK AUTHORITY.

A Mars node may only know:
  Earth chain height H.

It may:
  create local social objects;
  queue transactions anchored at H.

It does not claim:
  H is current global truth forever.

D28-84 — CONSENSUS COMMITTEE DOES NOT WAIT FOR INTERPLANETARY NODES.

Do not include a validator in a synchronous finality committee if its current
link cannot meet the consensus protocol's timing assumptions.

This is not disenfranchisement by wealth.

It is a physics constraint.

Long-term interplanetary political equality is handled through asynchronous
governance windows, not by breaking BFT liveness.

17. GOVERNANCE OVER LONG DELAY

D28-85 — "SENT BEFORE DEADLINE" IS NOT ENOUGH.

A vote/proposal action counts only if:
  canonical governance rules accept/include it by the canonical deadline.

A local queue timestamp:
  cannot create retroactive global votes.

D28-86 — UI HAS FOUR GOVERNANCE STATES.

  DraftLocal
  QueuedForSubmission
  Included
  Finalized / Counted

Never label:
  QueuedForSubmission
as:
  Voted
without qualification.

D28-87 — EARTH/DISASTER-INCLUSIVE GLOBAL GOVERNANCE WINDOW FLOOR: 30 DAYS.

For current terrestrial Mininet:
  ordinary global constitutional/protocol voting windows must be at least
  30 days if the system claims meaningful disaster-partition inclusion.

Existing longer timelocks:
  remain longer.

D28-88 — INTERPLANETARY-INCLUSIVE GOVERNANCE WINDOW FLOOR: 365 DAYS.

If a future network explicitly claims:
  humans behind deep-space/planetary DTN have equal practical opportunity to
  participate in one global governance action,
then:
  voting window >=365 days
unless a later evidence-backed transport reachability model proves a different
window still offers equivalent access.

This does NOT slow current Earth governance to one year.

The claim "interplanetary-inclusive" is optional until such populations exist.

D28-89 — LOCAL GOVERNANCE DISCUSSION IS FREE.

A disconnected community may:
  debate;
  draft;
  sign endorsements;
  prepare proposals.

It may govern:
  its own voluntary local application/community rules.

It cannot declare:
  local constitutional vote == global Mininet vote.

D28-90 — EMERGENCY AUTHORITY DOES NOT GROW DURING PARTITION.

Partition is a reason for:
  fewer irreversible powers,
not:
  founder/admin emergency powers.

No:
  satellite operator key;
  hotspot admin;
  "disaster controller"
may rewrite global monetary/governance rules.

19. STORAGE, MESSAGING, CRDT, AND FORGE SEMANTICS
======================================================================

D28-96 — CONTENT IS THE EASIEST AND SAFEST DTN CLASS.

Public content-addressed bytes:
  may be copied;
  stored;
  retransmitted;
  deduplicated
without changing their truth.

Receiver verifies:
  content ID.

If authorship matters:
  receiver also verifies signature/provenance.

D28-97 — PRIVATE MESSAGES REMAIN END-TO-END OBJECT ENVELOPES.

The existing private-message path already places message semantics inside an
encrypted `ObjectEnvelopeV2`.

DTN carries that opaque envelope.

A relay:
  does not receive the conversation key.

D28-98 — READ / DELIVERY RECEIPTS REMAIN APPLICATION OBJECTS.

A BP "delivered" status:
  is not the same as:
    Mininet message delivered/read receipt.

The latter remains:
  an encrypted/signed conversation object
under messaging semantics.

D28-99 — CRDT OPS ARE NATURALLY DELAY TOLERANT.

Signed CRDT operations may:
  arrive out of order;
  arrive repeatedly;
  merge after long partition.

The CRDT layer, not BP, decides:
  operation validity;
  causality;
  conflict-free merge semantics.

D28-100 — NON-CRDT APP POINTERS USE THEIR EXISTING SIGNED SEQUENCE/HEAD RULES.

A delayed old signed profile/head/reference must not overwrite a newer valid one
merely because it arrived later.

Transport arrival order:
  never becomes application logical order.

D28-101 — FORGE OBJECTS MAY TRAVEL OVER DTN.

Eligible:
  Git object/chunk;
  issue op;
  review;
  patch metadata;
  signed ref proposal;
  release artifact manifest.

Large repositories:
  use content-addressed chunk/object transfer;
  not one enormous bundle.

D28-102 — A DTN FORGE GATEWAY HAS ZERO MERGE AUTHORITY.

Carrying:
  a patch;
  a review;
  a signed release
does not authorize:
  merge;
  canonical ref update;
  protocol release.

Forge governance/verification remains unchanged.

D28-103 — SOFTWARE UPDATE DELIVERY DOES NOT MEAN SOFTWARE UPDATE ADOPTION.

A delayed bundle can carry:
  release metadata;
  binary;
  source;
  transparency proof.

Client still verifies:
  expected content hash;
  signatures/governance authorization;
  reproducibility evidence as required.

There is no:
  satellite-provider update key;
  disaster-admin forced update.

  `StoredLocal`

  QueuedLocal

  StoredLocal.

D28-106 — CRASH RECOVERY IS REPLAY-SAFE.

  durable bundle records reload;
  incomplete records do not become valid bundles;
  complete duplicate records collapse by bundle/application IDs;
  no payment becomes final due recovery.

D28-107 — QUEUE METADATA IS VERSIONED AND CHECKSUMMED.

Minimum persistent record contains:

  format version;
  bundle identifier;
  application content identifier when known;
  payload reference;
  payload length;
  priority class;
  BP creation/age basis;
  transport expiration;
  hop state;
  source/destination EIDs;
  current forwarding status;
  retry/contact state;
  checksum / record integrity field.

D28-108 — PAYLOAD IS CONTENT-ADDRESSED LOCALLY WHERE PRACTICAL.

For a Mininet application object:
  store one content-addressed blob;
  queue records reference it.

Multiple BP copies:
  need not duplicate the bytes.

D28-109 — GC IS TRANSACTIONAL.

Garbage collection:
  first marks/removes queue references;
  then releases blob storage only when no local reference remains.

Crash during GC:
  may leak disk temporarily;
  may not make a different blob appear under an old content ID.

D28-110 — A RELAY ACK IS NEVER ISSUED BEFORE THE CLAIMED LOCAL DURABILITY LEVEL.

If a future convergence/custody extension promises:
  "I have durable custody"

the implementation must persist before sending that promise.

V1:
  does not promise custody transfer by default.

D28-111 — LOCAL QUEUE CORRUPTION FAILS CLOSED FOR THE CORRUPT RECORD.

A corrupt queue entry:
  is quarantined/rejected.

It does not:
  crash the whole agent;
  reinterpret bytes as another bundle;
  silently submit partial money/governance objects.

D28-112 — DURABILITY DOES NOT MEAN FOREVER.

A properly stored bundle may later be deleted because:
  lifetime expired;
  local quota requires eviction;
  user cancels local copy;
  destination delivered;
  policy rejects it.

The status history should explain:
  why.

21. EVICTION / SCHEDULING / QUOTA DECISION
======================================================================

D28-113 — EXPIRY FIRST.

When freeing transit queue space:

  1. delete expired/ineligible bundles;
  2. delete invalid/corrupt/quarantined entries;
  3. collapse redundant duplicates;
  4. apply class-aware eviction.

D28-114 — BULK IS EVICTED BEFORE HUMAN-CONTROL TRAFFIC UNDER PRESSURE.

For TRANSIT copies only, default eviction preference:

  P3 bulk first;
  P2 interactive next;
  P1 human-control/canonical-submission next;
  P0 safety/control last.

Within class:
  shortest remaining useful lifetime;
  least unique route/copy value;
  oldest local enqueue
may inform deterministic/local policy.

D28-115 — USER-OWNED ORIGINALS ARE NOT TRANSIT CACHE.

Deleting a transit bundle to protect disk:
  cannot delete the user's sole original message/object from its application
  store.

DTN queue:
  references application objects.

It does not become:
  an owner with unilateral delete rights over source data.

D28-116 — LOCAL USER MAY PIN SELECTED OUTBOUND BUNDLES.

A user may designate:
  "keep my local source copy while still valid."

Pinning:
  consumes their local storage;
  does not force any other relay to retain it.

D28-117 — PAID STORAGE DOES NOT BUY CONTROL PRIORITY.

A user may directly pay another human-operated service for extra storage under
ordinary free-market terms.

That does not alter:
  P0/P1/P2/P3 protocol semantics;
  application truth;
  governance;
  finality.

A commercial DTN courier can exist.

It does not become a Mininet authority.

D28-118 — TRANSIT QUOTAS MAY BE TUNED LOCALLY.

The defaults in Section 10 are recommended mobile safety values.

A 64-TB community node may configure much larger queues.

A 4-GB old phone may disable transit relaying entirely.

Both remain:
  valid Mininet participants.

22. CONTACT / CLOCK / SCHEDULE SEMANTICS
======================================================================

D28-119 — CONTACT WINDOW CLOCK IS ROUTING INPUT, NOT CANONICAL TRUTH.

Scheduled routing needs a usable clock.

If the local clock is wrong:
  a contact may be missed;
  scheduling may be inefficient.

It cannot:
  make an expired canonical payment valid;
  create a vote;
  change chain height.

D28-120 — UNSCHEDULED TERRESTRIAL MODE MUST NOT REQUIRE CLOCK SYNCHRONIZATION.

Opportunistic contacts use:
  actual link availability;
  monotonic local durations;
  Bundle Age.

No:
  NTP;
  GPS;
  cell tower
is mandatory for basic disaster store-carry-forward.

D28-121 — CONTACT PLAN ENTRY.

Conceptual entry:

  Contact {
      from_eid,
      to_eid,
      start_time,
      end_time,
      capacity_bytes,
      nominal_rate_bps,
      one_way_light_time_ms,
      confidence_ppm,
      source_id,
  }

The routing engine treats it as:
  forecast.

D28-122 — CAPACITY IS EXPLICIT.

Scheduled route calculation must account for:
  contact duration;
  data rate;
  already-allocated queue;
  convergence-layer overhead estimate.

A 10-minute 8-kbit/s contact does not have infinite route capacity.

D28-123 — MISSED CONTACT DOES NOT DROP THE APPLICATION OBJECT.

If route A is unavailable:
  retain until:
    another route;
    later contact;
    expiration;
    quota eviction.

D28-124 — CONTACT-PLAN UPDATE DOES NOT REWRITE BUNDLE.

Only route plan/state changes.

Application object:
  immutable.

D28-125 — CLOCK ROLLBACK IS BOUNDED.

For bundle-age accounting:
  use durable accumulated monotonic age across process restarts where feasible;
  do not reduce recorded Bundle Age merely because wall clock moves backward.

D28-126 — CLOCK JUMP FORWARD MAY EXPIRE TRANSPORT BUT NOT APPLICATION TRUTH.

If a bad local wall clock causes local transport expiry:
  that local copy may be lost.

It cannot:
  invalidate a globally finalized transaction;
  revoke an identity;
  rewrite an object.

24. QUANTITATIVE LINK / PAYLOAD CALCULATIONS
======================================================================

These calculations are included so the size decisions are inspectable.

Ignoring protocol overhead:

64 KiB:
  524,288 bits.

At:
  2 kbit/s   -> 262.144 s  = 4.37 min
  8 kbit/s   ->  65.536 s  = 1.09 min
  32 kbit/s  ->  16.384 s
  128 kbit/s ->   4.096 s
  1 Mbit/s   ->   0.524 s

1 MiB:
  8,388,608 bits.

At:
  2 kbit/s   -> 4,194.3 s = 69.9 min
  8 kbit/s   -> 1,048.6 s = 17.5 min
  32 kbit/s  ->   262.1 s = 4.37 min
  128 kbit/s ->    65.5 s
  1 Mbit/s   ->     8.39 s

8 MiB:
  67,108,864 bits.

At:
  8 kbit/s   -> 8,388.6 s = 2.33 h
  32 kbit/s  -> 2,097.2 s = 34.95 min
  128 kbit/s ->   524.3 s = 8.74 min

Therefore:

  64 KiB control cap:
    reasonable for extremely weak links.

  1 MiB general deferred payload:
    large enough for useful objects;
    small enough to fit many terrestrial/scheduled contacts.

  8 MiB global Mininet object:
    should travel as application chunks/manifests under extreme links.

D28-128 — PROTOCOL OVERHEAD IS MEASURED, NOT ASSUMED ZERO.

All test reports include:
  application bytes;
  BP bytes;
  convergence-layer bytes where measurable;
  retransmitted bytes;
  delivered useful bytes.

Efficiency is:

  useful application bytes delivered /
  total bytes sent on constrained link

for the stated test.

No marketing-only:
  "payload throughput"
that hides retries/headers.

25. RELIABILITY AND DELIVERY ACCEPTANCE
======================================================================

D28-129 — NO UNIVERSAL "100% DELIVERY" PROMISE.

A bundle can legitimately fail because:
  no future contact;
  lifetime ends;
  every relay deletes it;
  destination disappears;
  quota rejects it;
  adversary jams/drops.

Mininet promises:
  explicit states;
  retry/carry under policy;
  no false finality.

D28-130 — REQUIRED TEST DELIVERY TARGETS.

For P0/P1 64-KiB-or-smaller objects with lifetime long enough for the test:

  D1:
    >=99.9% application-accepted within 24 hours.

  D2:
    >=99.0% within 72 hours.

  S1:
    >=99.9% within 12 hours.

  L1:
    >=99.0% within 48 hours.

  M1/M2:
    >=99.0% by end of 30-day fixture if cumulative contact capacity exceeds
    offered load by >=2x.

  M3:
    >=99.0% of still-unexpired P0/P1 objects by seven days after the blackout
    ends if cumulative contact capacity exceeds surviving offered load by >=2x.

X1:
  no universal delivery-rate threshold for bulk.
  P0/P1 must make deterministic progress and must not be starved while adequate
  cumulative contact capacity exists.

These are Mininet engineering targets, not laws of physics.

D28-131 — OFFERED LOAD MUST BE REPORTED.

A test that offers:
  10x more data than the link can ever carry
cannot report:
  "DTN failed reliability"
without separating overload from protocol failure.

Report:
  offered load;
  theoretical contact capacity;
  protocol bytes;
  accepted load;
  delivered load.

D28-132 — DUPLICATES DO NOT COUNT AS EXTRA SUCCESS.

Application-accepted unique content IDs:
  numerator.

Duplicate deliveries:
  reported separately.

D28-133 — EXPIRED BUNDLES ARE NOT SILENT LOSS.

Final local status:
  ExpiredTransport

with:
  bundle ID;
  application ID if known;
  expiry reason;
  last forwarding attempt summary.

26. WEAK-DEVICE PERFORMANCE TARGETS
======================================================================

D28-134 — THE DTN CORE MUST RUN ON A 4-GIB-RAM ANDROID-CLASS DEVICE.

This is a compatibility target, not a requirement to run a spacecraft modem on
Android.

The phone must be able to:
  enqueue;
  persist;
  schedule;
  dedupe;
  transfer
its configured 512-MiB-or-smaller transit queue.

D28-135 — STREAM, DO NOT MATERIALIZE THE WHOLE QUEUE.

A 1 MiB bundle may be streamed.

A 512 MiB queue:
  must not become:
    512 MiB RAM.

D28-136 — METADATA INDEX TARGET.

With:
  10,000 queued bundle records
and payloads stored separately:

  queue metadata resident memory target:
    <=128 MiB additional process memory.

A phone implementation exceeding this:
  is not V1 weak-device compliant.

D28-137 — RESTART TARGET.

After clean or crash recovery with:
  10,000 records / <=512 MiB payload store:

  usable scheduler state:
    <=10 seconds on the project's reference weak Android/Linux-class test
    device.

Lazy index loading is allowed.

D28-138 — IDLE MODE DOES NOT POLL SPIN.

With no active contact:
  no busy loop.

Use:
  timers;
  OS wakeups;
  contact events.

D28-139 — CONTACT CPU DOES NOT BLOCK UI.

Mobile UI thread:
  never performs bundle parsing/BPSec/hashing of large payload synchronously.

D28-140 — BATTERY TEST.

On Android-class device:

  8-hour no-contact DTN-enabled idle period
versus:
  DTN-disabled matched control.

Target incremental battery use:
  <=3 percentage points of full battery capacity.

If platform measurement noise is higher:
  use repeated runs and report confidence/range.

D28-141 — USER CONTROLS CELLULAR / METERED USE.

Default mobile policy:

  P0/P1:
    may use metered network if user has enabled DTN background transport.

  P2:
    user configurable.

  P3:
    unmetered/charging by default.

No central policy:
  forces a poor user to spend a metered data plan carrying bulk traffic.

D28-142 — THERMAL FAILURE DEGRADES SERVICE, NOT TRUTH.

If device enters severe thermal state:
  pause P3 first;
  reduce forwarding;
  keep bounded P0/P1 opportunity where safe.

Never:
  skip signature verification
to save CPU.

33. EXACT CODE CHANGE MAP
======================================================================

This is implementation guidance, not a requirement that terrestrial mainnet
wait for the code.

33.1 ADD `crates/mini-dtn`

Primary responsibility:
  RFC9171 bundle codec;
  deferred queue;
  routing;
  convergence-layer interface;
  application parcel dispatch;
  interop test vectors.

This crate must be:
  Rust;
  `#![forbid(unsafe_code)]` unless a separately reviewed low-level platform
  boundary proves a necessity;
  no daemon/server required for ordinary library use.

33.2 `mini-dtn::bpv7`

Implement only the standards profile Mininet needs first:

  primary block;
  payload canonical block;
  generic extension-block preservation/processing;
  Bundle Age;
  Hop Count;
  CRC profiles;
  endpoint IDs;
  creation timestamp/lifetime;
  status-report parsing sufficient for interoperability;
  fragmentation receive only if explicitly enabled.

Do not initially implement every historical BP feature.

33.3 `mini-dtn::queue`

Use:
  `mini-durable`
for owner-controlled filesystem commitment primitives.

The current `mini-durable` already provides:
  stable locks;
  atomic file replacement;
  file flush;
  parent directory flush;
  fail-closed unsupported durability behavior.

Build:
  queue journal/index;
  content blob store;
  quota tracker;
  admission;
  scheduler;
  GC
on those primitives.

Do not reinvent a weaker:
  write(temp); rename(); "probably fine"
path.

33.4 `mini-dtn::cla`

Trait concept:

  trait ConvergenceLayer {
      fn capabilities(&self) -> ClaCapabilities;
      fn offer_contact(&mut self, contact: Contact) -> Result<()>;
      fn send_bundle(&mut self, id: &BundleId, reader: &mut dyn Read)
          -> Result<TransferOutcome>;
      fn receive_bundle(&mut self, sink: &mut dyn BundleSink)
          -> Result<Option<TransferOutcome>>;
  }

First:
  TCPCLv4.

Then:
  existing Bearer contact adapter.

Future:
  LTP;
  QUICCL;
  BTP-U.

CLA must stream payload.

33.5 `mini-dtn::route`

V1:
  direct destination;
  bounded opportunistic spray-and-wait;
  scheduled contact-plan route.

Keep routing policy local.

Do not serialize:
  one node's "best route"
as globally authoritative application truth.

33.6 `mini-dtn::app`

`DeferredParcel` should bind:

  application service/type;
  immutable application bytes or content reference;
  semantic content ID where known;
  priority class derived by app policy;
  lifetime class;
  destination opaque DTN capability/EID;
  optional source EID;
  requested security profile.

Bundle construction:
  deterministic except fields that BP legitimately assigns locally.

33.7 `mini-objects`

No object-format rewrite is required merely for DTN.

Add helper if useful:

  `DeferredObjectRef`
or:
  `to_deferred_payload()`

But keep:
  Object ID;
  ObjectEnvelopeV2
unchanged.

33.8 `mini-messaging`

Add optional deferred-send transport integration.

Do not change:
  conversation encryption key
because the message travels by BP.

Message send state:
  LocalStored
  DeferredQueued
  DeliveredToConversation
  Read
as separate UI/application facts.

33.9 `mini-sync`

Allow:
  sync requests/manifests/chunk inventories
to be represented as deferred application operations.

Do not require:
  live request-response
for full state reconciliation.

33.10 `mini-settlement`

ADD:
  PaymentClaimV2;
  ChainAnchorV2;
  canonical economic-epoch validity.

KEEP:
  current canonical `reconcile()` principle.

Refactor, if necessary, so both V1/V2:
  can only obtain `Finalized`
from canonical ledger view.

No DTN crate:
  imports an API that can create Finalized directly.

33.11 `mini-governance`

Expose transport-neutral:
  signed vote/proposal submission objects.

UI/API state:
  draft;
  queued;
  included;
  counted/finalized.

A relay delivery callback cannot call:
  `mark_vote_counted`.

33.12 `mini-presence`

No fresh physical presence protocol over DTN.

Only:
  transport an already-complete signed presence evidence object.

Explicit type-level separation preferred:
  `ArchivedPresenceEvidence`
or equivalent.

33.13 `mini-forge`

Use existing:
  content IDs;
  signed refs;
  CRDT/COB operation objects.

Deferred transport is an extra sync path.

No:
  DTN-specific merge authority.

33.14 storage fabric

Reuse:
  chunks;
  manifests;
  content-addressed blobs.

The DTN queue should point at existing content blobs where possible instead of
copying bytes into a second opaque storage silo.

33.15 platform/mobile

User controls:

  Enable delayed delivery
  Enable carrying transit bundles
  Transit storage budget
  Metered-network policy
  Charging-only bulk policy
  Diagnostics/export

No:
  silent default use of large cellular data for strangers' bulk bundles.

33.16 instrumentation

Export privacy-safe metrics:

  queue bytes;
  queue records;
  class counts;
  expired;
  evicted;
  duplicate;
  transferred bytes;
  retransmission bytes;
  contact durations;
  app accepted/rejected counts;
  delivery latency buckets.

Do not upload automatically.

37. RESIDUAL RISKS THAT THIS DESIGN DOES NOT PRETEND TO REMOVE
======================================================================

R28-01 PHYSICAL LINK DENIAL

A sufficiently powerful jammer, destroyed infrastructure, or absent satellite
can prevent delivery.

No routing algorithm creates a radio path from nothing.

Mitigation:
  multiple bearers;
  carry by humans/devices;
  opportunistic routing;
  delay.

Residual:
  unavoidable.

R28-02 TRAFFIC ANALYSIS

Even encrypted bundles expose:
  timing;
  size;
  EIDs/contact patterns
to some observers.

Mitigation:
  opaque/rotating endpoints;
  object encryption;
  optional mix/tunnel layers;
  padding at higher privacy cost.

Residual:
  not fully solved.

R28-03 PATIENT DROP CENSORSHIP

A region with only one physical gateway can be censored by that gateway.

Protocol cannot create route diversity where geography has none.

Mitigation:
  user-carried copies;
  multiple providers;
  local social function;
  eventual alternative path.

Never solve with:
  "trusted official gateway."

R28-04 OFFLINE DOUBLE-SPEND RISK

If two merchants explicitly accept the same payer's conflicting signed claims
before canonical finality, at least one may lose.

Mitigation:
  default early acceptance=0;
  watcher;
  small user-set risk limit;
  chain anchor;
  expiry;
  canonical reconciliation.

Residual:
  inherent to offline acceptance of a globally scarce asset.

R28-05 ROUTING-PLAN ERROR

Scheduled contact plans can be wrong.

Mitigation:
  local validation;
  alternate plans;
  dynamic contact observations;
  no authority semantics.

R28-06 BPSec KEY MANAGEMENT

RFC9172/9173 do not magically solve universal key distribution.

Mitigation:
  local/mission/pairwise security policy;
  Mininet application crypto independently protects its own semantics.

R28-07 PLANETARY POLITICAL LATENCY

Physics can make a single global governance event inconvenient over planets.

Mitigation:
  long windows when claiming global interplanetary inclusion;
  asynchronous proposals;
  local voluntary community autonomy.

Residual:
  real light-time cannot be abstracted away.

R28-08 HARDWARE / OPERATING-SYSTEM STORAGE LOSS

A phone can:
  die;
  be wiped;
  corrupt storage;
  be seized.

Mitigation:
  multiple voluntary copies;
  content addressing;
  re-forwarding;
  user backup.

No:
  central recovery custodian.

R28-09 RESOURCE-EXHAUSTION ATTACKS

An attacker can generate many syntactically valid bundles.

Mitigation:
  quotas;
  size bounds;
  admission;
  priority validation;
  rate limits;
  local user choice.

Residual:
  a fully saturated physical link cannot carry infinite legitimate traffic.

R28-10 STANDARDS EVOLUTION

DTN standards are actively evolving in 2026.

Mitigation:
  BPv7/RFC9171 stable core;
  adapter architecture;
  explicit experimental status for drafts;
  no draft in consensus.

38. WHAT REOPENS THIS DOMAIN-DESIGN GATE
======================================================================

Gate #28 design review reopens only if Mininet proposes a MATERIAL departure from
these settled boundaries, including:

  * replacing RFC9171 BPv7 with a bespoke incompatible deferred protocol;
  * making a DTN relay/gateway a trust root;
  * allowing local partition finality for the same global MINI asset;
  * merging balance ledgers by CRDT;
  * treating BP delivery/custody as money finality;
  * making contact plans consensus authority;
  * making a satellite/provider EID personhood/governance authority;
  * making a central key/certificate server necessary for Mininet identity;
  * removing the distinction between transport lifetime and canonical
    application validity;
  * allowing wall-clock relay time to decide canonical payment expiry;
  * making an Internet-Draft experimental CLA consensus-critical;
  * making users forcibly store/relay other people's data;
  * making DTN priority purchasable in a way that affects governance rights;
  * requiring deep-space nodes inside a synchronous finality round whose
    physics cannot meet the round timing;
  * claiming interplanetary global voting equality with windows too short for
    the supported reachability model;
  * substantially raising untrusted bundle/resource limits without a new DoS
    analysis.

The gate does NOT reopen merely because:

  * a new convergence layer is added behind the same interface;
  * a new satellite provider appears;
  * a new contact plan is used;
  * a better open routing algorithm replaces spray-and-wait;
  * an RFC draft becomes a final RFC and the adapter is updated;
  * an external BP implementation changes version;

41. OVERALL JUDGMENT
======================================================================

DOES THE EXTREME-ENVIRONMENT ARCHITECTURE IN THIS REPORT SERVE A FREE INTERNET
FOR HUMANITY?

YES.

It serves the project values because:

  * Mininet does not invent a proprietary "space internet" protocol;
  * it uses RFC9171 BPv7, with RFC9172/9173/9174 where appropriate;
  * NASA/CCSDS implementations are interoperability peers, not authorities;
  * a satellite route is just another route;
  * a satellite owner receives no political standing;
  * a contact plan is advice, not truth;
  * private Mininet content remains encrypted through untrusted gateways;
  * users are not forced to relay/store strangers' data;
  * weak phones can use bounded queues;
  * disruption does not manufacture emergency founder/admin power;
  * application objects can reconcile asynchronously;
  * money does not pretend double-spends can be CRDT-merged;
  * local payment acceptance is visibly risk, not false finality;
  * canonical chain proof remains the only global monetary truth;
  * long light-time changes scheduling and governance windows, not human worth;
  * the core works without NASA, one satellite provider, a PKI operator, or a
    centralized time server.

42. AUDITOR / DOMAIN-EXPERT ADOPTION
======================================================================

I have reviewed the Mininet extreme-environment / DTN architecture and adopt
this report as the final domain design decision for Gate #28.

I specifically adopt:

  [ ] RFC 9171 Bundle Protocol Version 7 as the deferred interoperability base.

  [ ] A separate asynchronous `mini-dtn` layer instead of changing the live
      `mini_bearer::Bearer` into a persistent protocol.

  [ ] RFC 9174 TCPCLv4 as the first required native IP interoperability
      convergence layer.

  [ ] RFC 9172/9173 BPSec as optional bundle-layer security while Mininet
      application objects retain independent end-to-end security.

  [ ] Disaster/opportunistic terrestrial operation as the first implementation
      target.

  [ ] Scheduled satellite/lunar operation as the second target.

  [ ] Deep-space/Mars as an architectural/emulation target that does not block
      terrestrial launch.

  [ ] No same-global-MINI locally canonical partition ledger.

  [ ] Local signed payment acceptance remains nonfinal risk.

  [ ] PaymentClaimV2 uses a canonical chain anchor and economic-epoch validity,
      with a maximum twelve-epoch validity interval.

  [ ] Bundle delivery or custody is never monetary finality.

  [ ] Content/CRDT state may reconcile; canonical balances/governance execution
      do not CRDT-merge.

  [ ] Transport lifetime is separate from payment/governance/application
      validity.

  [ ] The Mininet DTN application profile has a 1MiB payload ceiling and64KiB
      control ceiling; larger data uses content-addressed chunks/manifests.

  [ ] Normal generated hop limit32; scheduled/deep-space generated hop limit64.

  [ ] Bundle lifetimes:
      1h /24h /30d /180d /365d by class.

  [ ] Store-carry relay is voluntary and bounded; mobile default transit quota is
      min(512MiB,10% free storage) subject to the free-space floor.

  [ ] Functional scheduling priority is not purchasable.

  [ ] Work-conserving DRR4:3:2:1 prevents critical traffic from being buried
      while retaining bulk progress.

  [ ] Opportunistic V1 uses bounded spray-and-wait; scheduled deployments may use
      SABR/CGR-compatible contact-plan routing.

  [ ] Contact plans and public EID allocators create no Mininet authority.

  [ ] Private Mininet users do not expose a stable did:mini root as their default
      BP EID.

  [ ] Custody transfer is optional/experimental, not required by the base API.

  [ ] LTP is an optional space-link convergence technology.

  [ ] Current QUICCL/BTP-U/BIBE work remains experimental until adopted at an
      appropriate standards/support level.

  [ ] Physical presence cannot be fabricated by delayed transport.

  [ ] Terrestrial disaster-inclusive global governance claims use a >=30-day
      voting window; future interplanetary-inclusive claims use >=365 days unless
      an evidence-backed later model provides equivalent access.

  [ ] Gate #28 is a non-blocking architecture gate and closes with this adoption;
      actual feature support requires implementation evidence, not another generic
      DTN design review.
