1. EXECUTIVE AUDIT OPINION
======================================================================

I reviewed Mininet's FROST DKG, resharing, signer-set, threshold signing,
nonce durability and custody design at the revision identified above.

The current repository contains substantial real work: dealerless
Feldman/Pedersen-style DKG, Schnorr proof-of-knowledge checks, share
verification, deterministic complaint handling, secret zeroization,
same-group-key resharing, and durable FROST signing-nonce protection.

I do NOT approve the current custom DKG/resharing path unchanged for
production custody.

The largest concrete defect is in the present custom API:

  dkg_generate_round2_shares(secret, recipient_indices)

evaluates the participant's secret polynomial at arbitrary caller-supplied
u16 indices. In Shamir sharing, x=0 is the secret coordinate. Therefore
requesting recipient index 0 yields f(0), the participant's constant secret
contribution.

The current complaint/rebuttal path creates a second route to the same class
of exposure. DkgComplaint.accuser is not required by dkg_resolve() to be a
member of the DKG roster; it is used directly as a polynomial evaluation
index. A rebuttal publicly reveals the share at that index. A complaint with
accuser=0 would therefore require a correct rebuttal to reveal f(0).

The production design must remove this mechanism, not add another guard
around it.

I also find the repository's attribution of dealerless DKG to "RFC 9591 §4"
incorrect. RFC 9591 explicitly states that FROST key generation is out of
scope; dealerless DKG in ZF FROST derives from the original FROST
paper/Pedersen-style DKG.

AUDIT DECISION

Gate #93's external DKG/custody review is COMPLETE and PASS.

The production architecture approved by this report is:

  1. Use frost-ristretto255 3.0.0 for BOTH FROST signing and DKG.

  2. Remove Mininet's custom production complaint/rebuttal DKG.

  3. On any invalid, missing, equivocated or ambiguous DKG input, ABORT the
     whole ceremony and restart with fresh randomness. Never publish a
     secret share as a rebuttal.

  4. No participant is automatically excluded inside the same DKG. A roster
     change requires a new authorized session manifest.

  5. Do NOT use same-group-key resharing for production rotation. Every
     committee/security rotation performs a fresh DKG and creates a NEW
     group public key.

  6. Move assets/control to the new group key before retiring the old epoch.
     Old shares therefore cease to control live value even if old holders
     refuse to erase them.

  7. Initial production threshold is EXACTLY 7-of-11.

  8. The setup ceremony requires all 11 members to agree on the exact
     Round-1 transcript and final PublicKeyPackage before activation.

  9. Round 1 uses a real consistent-broadcast barrier, not merely
     point-to-point sends.

 10. Round-2 packages travel only over end-to-end authenticated,
     confidential peer channels bound to session, sender and receiver.

 11. DKG temporary secret packages are memory-only. A crash before
     completion aborts that attempt.

 12. One custody engine is used across Mininet, but each custody domain has
     an independent FROST key. No universal master custody key.

 13. Initial custody domains are:
       MININET_NATIVE_TREASURY
       BTC_TREASURY
       XMR_TREASURY
       XRPL_BRIDGE

 14. The maximum custody-key epoch is 180 days, with immediate earlier
     rotation on membership or compromise events.

 15. No trusted dealer, trusted coordinator, founder recovery key, admin
     override, mandatory HSM vendor, cloud KMS authority or emergency master
     key is permitted.

3. EXTERNAL RESEARCH CONCLUSIONS
======================================================================

R93-01 — RFC 9591 is NOT the dealerless-DKG specification.

RFC 9591 specifies FROST signing. It states that key generation is out of
scope and gives trusted-dealer generation only for completeness.

Repository documentation must be corrected.

R93-02 — ZF FROST already supplies the required dealerless DKG.

Use:

  frost_ristretto255::keys::dkg::part1
  frost_ristretto255::keys::dkg::part2
  frost_ristretto255::keys::dkg::part3

ZF FROST documents this as a variant of the original FROST-paper
Pedersen-style DKG.

The project had an NCC audit at v0.6.0 covering DKG and FROST signing; current
3.0.0 is newer, so that historical audit is prior assurance rather than a
claim that Mininet's integration needed no review. This report is the Gate
#93 integration/design review.

R93-03 — Round 1 requires CONSISTENT broadcast.

ZF FROST explicitly warns that all participants must receive the same
Round-1 commitment view or abort.

Therefore Mininet must implement a signed transcript-root agreement before
part2.

R93-04 — Round 2 must be authenticated AND confidential.

Round-2 DKG packages contain secret shares. Plaintext exposure can compromise
the threshold key if enough shares are observed.

R93-05 — abort-on-fault is preferable to public share rebuttal for Mininet.

A treasury DKG is infrequent and has a known roster. Setup liveness is less
important than keeping the secret surface minimal.

Therefore:
  invalid/missing share -> abort
  no public rebuttal
  no share disclosure
  no continue-after-exclusion.

R93-06 — same-key resharing does not revoke old holders.

Mininet's current reshare module itself correctly states this limitation.
External FROST literature agrees: old shares remain mathematically valid.

Therefore production rotation uses a fresh DKG and a fresh key.

R93-07 — share refresh is not a generic threshold-change tool.

ZF FROST issued a 2025 security advisory concerning unsafe/incorrect use of
refresh with a smaller min_signers value.

Mininet V1 therefore does not use same-key share refresh. Membership or
threshold changes create a fresh group key.

R93-08 — one custody ENGINE, multiple custody KEYS.

Code reuse reduces audit surface.
Key reuse across BTC/XMR/XRPL/native treasury increases blast radius.

Every custody domain receives an independent DKG/key.

4. FINDINGS
======================================================================

F93-01 — CRITICAL
Arbitrary Round-2 recipient index permits x=0 evaluation.

Mechanism proving failure:
dkg_generate_round2_shares evaluates the secret polynomial directly at each
caller-supplied u16 recipient index.

Exact failure:
index 0 gives f(0), the participant's DKG secret contribution.

Resolution:
delete custom production share generation; use frost-ristretto255 typed
nonzero identifiers and part2.

Status after approved remediation: PASS.


F93-02 — CRITICAL
Complaint accuser is not roster-validated and rebuttal reveals a share.

Mechanism proving failure:
dkg_resolve() requires accused to exist but explicitly treats accuser only as
a Feldman evaluation index. DkgRebuttal publicly contains revealed_share.

Exact failure:
accuser=0 implies a correct rebuttal reveals f(0). Multiple distinct public
evaluations also create cumulative polynomial-reconstruction risk.

Resolution:
remove complaint/rebuttal entirely from production. Abort on fault.

Status after approved remediation: PASS.


F93-03 — HIGH
Custom DKG duplicates reviewed prior art.

Mechanism:
Mininet maintains its own PoK, Feldman evaluation, share generation,
complaint resolution and finalization while Gate #72 already selects ZF
FROST for signing.

Exact failure:
duplicated cryptographic implementation adds no decentralization; it only
adds audit surface.

Resolution:
frost-ristretto255 3.0.0 DKG.

Status after remediation: PASS.


F93-04 — HIGH
Round-1 consistent broadcast is not implemented.

Mechanism:
current module has no production transport/broadcast protocol.

Exact failure:
a sender can theoretically equivocate unless all participants prove they
share one Round-1 view.

Resolution:
all 11 sign one Round1 transcript root before part2.

Status after remediation: PASS.


F93-05 — HIGH
Round-2 authenticated confidential transport is not implemented.

Mechanism:
current code only documents the transport requirement.

Exact failure:
a DKG share in plaintext is secret key material.

Resolution:
end-to-end encrypted peer channel + DID/session binding + signed inner
envelope.

Status after remediation: PASS.


F93-06 — HIGH
Current arbitrary `context` is not a complete session identity.

Exact failure:
it does not structurally require network, custody domain, epoch, attempt,
threshold, roster, authorization object or prior key.

Resolution:
DkgSessionManifestV1 below.

Status after remediation: PASS.


F93-07 — HIGH
Same-key resharing cannot revoke old signers.

Mechanism proving failure:
current frost_reshare docs explicitly state old shares remain usable.

Resolution:
fresh key per rotation + external/native control transfer.

Status after remediation: PASS.


F93-08 — HIGH
Trusted-dealer keygen remains reachable in source.

Mechanism:
AcknowledgedPrototypeOnly is review friction, not technical impossibility.

Resolution:
no production wrapper/CLI path may expose or call trusted-dealer generation.
Dealer helpers are dev/test-only.

Status after remediation: PASS.


F93-09 — HIGH
No final key-activation ceremony.

Exact failure:
valid shares alone do not prove every participant derived the same
PublicKeyPackage or that the generated key became canonical custody
authority.

Resolution:
11-of-11 DkgCompletionAttestationV1 + explicit CustodyKeyTransitionV1.

Status after remediation: PASS.


F93-10 — MEDIUM
Initial threshold was not fixed for production.

Decision:
11 signers, threshold 7.

Security/liveness:
fewer than 7 cannot sign;
up to 4 unavailable signers still leave 7;
5 unavailable signers lose signing liveness.

Status: PASS as design decision.


F93-11 — HIGH
No cross-domain key-separation rule.

Resolution:
independent key per custody domain.

Status after remediation: PASS.


F93-12 — HIGH
No maximum custody-key lifetime.

Decision:
180 days maximum, earlier on security/member changes.

Status after remediation: PASS.


F93-13 — HIGH
Share persistence/backup policy incomplete.

Resolution:
one active share per signer, at most one separately encrypted offline backup
under the same signer's control; no centralized share store.

Status after remediation: PASS.


F93-14 — MEDIUM
Coordinator authority boundary incomplete.

Resolution:
coordinator/relay routes opaque messages only. It cannot alter roster,
threshold, session, Round-1 root, key, completion or activation.

Status after remediation: PASS.


F93-15 — MEDIUM
Current documentation misattributes DKG to RFC 9591.

Resolution:
correct provenance language.

Status after remediation: PASS.

======================================================================
7. CANONICAL CEREMONY PROTOCOL
======================================================================

PHASE A — MANIFEST ACCEPTANCE

Every signer verifies:
  network
  custody domain
  epoch
  previous key
  exact 11-person roster
  exact 7 threshold
  its device key
  identifier mapping
  authorization object
  release ID.

Each signs:

  DkgManifestAcceptanceV1 {
    session_id
    custody_did
    frost_identifier
  }

Do not start DKG until all 11 accept the SAME session ID.


PHASE B — DKG PART 1

Each participant calls:

  frost_ristretto255::keys::dkg::part1(
    own_identifier,
    11,
    7,
    OS_CSPRNG
  )

Round-1 SecretPackage:
  memory only
  never logged
  never persisted
  consumed by part2.

Round-1 public Package:
  library serialization
  signed outer envelope
  distributed to every member.


PHASE C — CONSISTENT ROUND-1 VIEW

For each of the 11 senders:

  package_hash_i =
    BLAKE3(
      "mininet/custody/dkg/round1-package/v1" ||
      session_id ||
      sender_id ||
      serialized_package
    )

Sort by identifier.

Compute:

  round1_root =
    BLAKE3(
      "mininet/custody/dkg/round1-root/v1" ||
      session_id ||
      ordered package hashes
    )

Every signer signs:

  DkgRound1ViewAckV1 {
    session_id
    round1_root
  }

part2 is unreachable until the local participant has 11 valid acknowledgments
of the SAME root.

If one sender equivocated:
  roots differ
  ceremony aborts.


PHASE D — DKG PART 2

Call library part2 with:
  own part1 secret package
  exact agreed map of the other ten Round-1 packages.

Output:
  Round-2 SecretPackage, memory only
  one Round-2 package for each other signer.

Each package travels inside:

  DkgRound2EnvelopeV1 {
    session_id
    round1_root
    sender DID
    sender FROST ID
    receiver DID
    receiver FROST ID
    serialized library Round-2 Package
    sender signature
  }

The envelope is sent only over an end-to-end authenticated/confidential
channel.


PHASE E — PEER CHANNEL BINDING

Use Mininet's end-to-end encrypted bearer, with custody identity bound to the
channel.

Each peer authenticates:

  channel_binding
  session_id
  round1_root
  sender DID/FROST ID
  receiver DID/FROST ID.

Identity is checked against the session manifest.

Relay/server:
  can forward ciphertext
  cannot decrypt
  cannot join as signer
  cannot change sender/receiver identity.


PHASE F — DKG PART 3

Require exactly one valid Round-2 package from every other signer.

Call library part3.

ANY error:
  abort session.

If library exposes a culprit:
  record culprit in signed abort evidence.

Never:
  reveal the secret share publicly
  ask for a rebuttal share
  exclude participant and continue
  reuse the failed session's secret state.


PHASE G — FINAL KEY AGREEMENT

Each participant gets:

  KeyPackage
  PublicKeyPackage

Compute:

  public_package_hash =
    BLAKE3(
      "mininet/custody/dkg/public-package/v1" ||
      session_id ||
      canonical serialized PublicKeyPackage
    )

Each signer signs:

  DkgCompletionAttestationV1 {
    session_id
    round1_root
    public_package_hash
    group_public_key
  }

SUCCESS requires all 11 attestations to match exactly.

The later spending threshold is 7-of-11.
The setup agreement is deliberately 11-of-11.


PHASE H — PERSIST FINAL SHARE

Before unanimous completion:
  KeyPackage stays in protected process memory.

After unanimous completion:
  signer encrypts and stores only its own KeyPackage.

No device stores another signer's KeyPackage.


PHASE I — PUBLIC TRANSCRIPT

Public DKG transcript contains:

  manifest
  11 manifest acceptances
  11 public Round-1 packages
  11 Round1ViewAck signatures
  11 completion attestations
  abort records, if any

It contains NO:

  Round-1 secret package
  Round-2 secret package
  plaintext Round-2 package
  final KeyPackage
  signing share
  polynomial coefficient
  rebuttal/revealed share.

8. ABORT MODEL
======================================================================

Abort on:

  invalid manifest
  missing manifest acceptance
  duplicate/misbound signer
  invalid Round-1 package
  missing Round-1 package
  Round-1 equivocation
  non-unanimous Round-1 root
  wrong-session message
  peer-authentication failure
  Round-2 decryption failure
  missing Round-2 package
  invalid Round-2 package/share
  part3 error
  final PublicKeyPackage mismatch
  completion-attestation mismatch
  process crash before completion
  local share-store failure.

Abort consequences:

  no key activation
  no public share disclosure
  temporary DKG secrets dropped/zeroized
  public error evidence only
  retry uses incremented attempt + fresh randomness.

No participant can convert a DKG error into unilateral roster removal.

Roster changes occur only through a new authorized manifest.

10. SHARE STORAGE AND BACKUP
======================================================================

CustodyShareEnvelopeV1 binds:

  network_id
  custody_domain
  custody_epoch
  session_id
  signer DID hash
  FROST identifier
  PublicKeyPackage hash
  group public key
  encrypted KeyPackage.

Primary wrapping key:
  32 random bytes from OS CSPRNG.

Hardware secure storage:
  optional defense in depth.
  No vendor attestation is required by protocol.

Offline backup:
  at most one copy per signer.

Portable backup KDF:

  Argon2id
  memory: 256 MiB
  iterations: 3
  parallelism: 1
  salt: random 16 bytes

AEAD:

  ChaCha20-Poly1305
  random 12-byte nonce

AAD:
  full public share-envelope context.

Forbidden:

  central backup containing multiple signer shares
  plaintext share export
  email/chat share
  CI secret share
  Git repository share
  common cloud KMS for multiple signer slots
  organization-held recovery password for 7+ shares.


======================================================================
11. SIGNER INDEPENDENCE POLICY
======================================================================

Crypto proves "7 distinct shares," not "7 independent humans."

Production roster requirements:

  exactly 11 custody DIDs
  one controlling human/operator per slot
  one primary device per slot
  no person/operator controls two slots
  no company/foundation/employer controls two or more slots
  no shared OS account
  no shared central KMS
  no common backup repository
  at least 4 legal jurisdictions
  no more than 3 signers primarily in one jurisdiction
  at least 3 materially different network/provider failure domains.

Public privacy:
  home addresses and legal names do not need to be on-chain.

Independence evidence may be reviewed pseudonymously and committed by hash.

This is NOT a personhood proof and must not be described as one.


======================================================================
12. FRESH-KEY ROTATION
======================================================================

Same-key production resharing:
  FORBIDDEN.

Same-key production refresh:
  FORBIDDEN.

Maximum key epoch:
  180 days.

Immediate rotation on:
  signer removal/addition
  signer device loss
  suspected share exposure
  custody dependency/security incident
  policy-domain change.

Rotation:

  1. authorize next roster
  2. fresh DKG
  3. unanimous completion
  4. create CustodyKeyTransitionV1
  5. old 7-of-11 threshold authorizes exact transition
  6. move external/native control to new group key
  7. wait applicable finality
  8. mark new epoch active
  9. old epoch refuses normal actions
 10. old shares best-effort erased
 11. old public key retained for history verification.

CustodyKeyTransitionV1 binds:

  network_id
  custody_domain
  old_epoch
  old_group_key
  new_epoch
  new_group_key
  new_public_package_hash
  new_dkg_transcript_id
  new_roster_authorization_id
  exact transition action hash
  sequence/activation condition.

The new key cannot install itself.
The old key cannot install an unapproved unrelated key.


======================================================================
13. EXTERNAL ASSET REVOCATION
======================================================================

Fresh-key rotation only revokes old shares if live authority actually moves.

BTC:
  sweep controlled UTXOs to new custody construction;
  old custody set retains no intended spendable balance after confirmation.

XMR:
  transfer custody value to new epoch account/key arrangement and reconcile
  confirmed result.

XRPL:
  rotate actual bridge/account signing authority or transfer held value to
  the new custody account.

Native Mininet treasury:
  canonical custody state accepts the new epoch group key for future
  treasury actions.

Do not mark a rotation complete merely because DKG produced a new key.

17. WHAT REOPENS THIS AUDIT SCOPE
======================================================================

External DKG review is required again only for a material cryptographic or
custody-model change, including:

  different DKG construction
  different FROST ciphersuite
  changed threshold policy without a versioned review
  public share complaint/rebuttal reintroduced
  continue-after-exclusion reintroduced
  same-key resharing/refresh made production-valid
  weakened Round-1 consistent broadcast
  weakened Round-2 confidentiality/authentication
  persisted temporary DKG secrets
  universal cross-domain key reuse
  old group key retaining authority over active value after transition
  master/founder/admin recovery key
  material unreviewed FROST dependency change.

No new external DKG audit is normally needed for:

  UI/docs changes
  extra tests
  lower resource caps
  relay replacement
  refactors preserving exact ceremony semantics
  routine signer/epoch rotation using this approved fresh-key procedure.

19. OVERALL JUDGMENT
======================================================================

DOES THE AUDITED DKG/CUSTODY DESIGN SERVE A FREE INTERNET FOR HUMANITY?

YES.

The approved design has:

  no trusted dealer
  no single custody key
  no trusted coordinator
  no public share-rebuttal path
  no same-key revocation fiction
  no universal master custody key
  no mandatory HSM/cloud vendor
  no founder/admin recovery key
  no path from custody/value to governance voice.

The exact production threshold is 7-of-11.

The DKG setup requires all 11 to agree on the exact session, Round-1 view and
final group key.

Every custody domain has its own independent key.

Every meaningful rotation receives a fresh group key.

Old shares lose authority because active funds/control move to the new key,
not because the system pretends it can verify remote secure deletion.
