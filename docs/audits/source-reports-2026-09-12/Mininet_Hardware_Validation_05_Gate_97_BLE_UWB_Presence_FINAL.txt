======================================================================
0. PURPOSE
======================================================================

Gate #97 cannot be closed by:

  source review;
  CI;
  an emulator;
  a Bluetooth mock;
  a loopback socket;
  a unit test;
  a screenshot;
  a successful Gradle compile;
  a vendor claim that UWB is secure;
  a vendor claim that Bluetooth Channel Sounding is centimeter-accurate;
  an AI review;
  a founder review;
  or a developer saying "works on my phone."

It exists specifically because Mininet makes a PHYSICAL claim:

  two independently controlled devices were sufficiently near one another
  during a mutually signed, channel-bound presence ceremony.

Radio behavior, OS scheduling, RF multipath, body blocking, permissions,
background restrictions, GATT behavior, UWB chipset behavior, Bluetooth
controller behavior and relay attacks are properties of real systems.

They are not established by type checking.

This package therefore converts the open-ended hardware requirement into an
exact release procedure.

It makes the design decisions now.

A human team may review and modify them BEFORE they enter the project.

After adoption, engineering should implement the decisions rather than reopen
the design.

The external/independent tester then measures the finished candidate on real
hardware.

That distinction matters:

  design review decides the protocol;
  hardware evidence decides whether the implementation matches reality.

CURRENT GATE #97 VERDICT:

  FAIL.

SPECIFIC MECHANISM PROVING THE FAILURE:

  `crates/mini-presence/src/ranging.rs` explicitly states that no real hardware
  ranging implementation ships and that `NoUwb` is the only reference source.

  Current `app/android` on main contains no Kotlin BLE GATT radio adapter and no
  Android ranging adapter.

  Current main Android manifest declares only INTERNET; it does not declare the
  Bluetooth Nearby Device permissions or Android 16 RANGING permission required
  by the intended path.

  `mini-presence::active_range` measures a real encrypted application-layer
  challenge/response RTT, but its own source documentation correctly states that
  it is NOT cryptographic distance bounding and does not defeat a low-latency
  relay/wormhole.

  Current `UwbRanging` contains only:
    distance_cm
    sample_count

  and `sample_count` is explicitly not independently checked by the current
  verifier.

  `PresenceVerdict::hardware_ranged` currently means only:
    an optional `uwb` field was present.

  It does not prove:
    which technology measured it;
    which hardware security mode was used;
    whether the measurement was session-bound;
    whether a secure STS existed;
    whether Bluetooth Channel Sounding attack detection passed;
    which side measured;
    whether enough samples existed;
    whether the distribution was sane;
    or whether the actual device pair survived relay testing.

  `TransportKind::InProcess` is currently treated as a proximity transport for
  CI, so release builds need a hard exclusion before "proximity" becomes a
  production-security claim.

CURRENT POSITIVE MECHANISMS:

  PASS — mutual signed presence transcript exists.

  PASS — device delegation and ATTEST capability are verified.

  PASS — fresh nonces are signed.

  PASS — expected encrypted-channel binding can be checked.

  PASS — a real active RTT challenge/echo is measured with the measuring
         device's monotonic clock.

  PASS — software RTT is always enforced before optional UWB tightening.

  PASS — replay state has a durable `FileReplayGuard` implementation.

  PASS — invalid/partial verification does not intentionally consume a valid
         presence result.

  PASS — the code itself admits software RTT cannot stop a fast relay.

These mechanisms are worth preserving.

They do not close the physical gate.

2. FINAL HARDWARE ARCHITECTURE DECISIONS
======================================================================

H97-01 — ANDROID IS THE GATE #97 V1 LAUNCH PLATFORM.

Decision:
  Android is the release-blocking mobile platform for Gate #97 V1.

Reason:
  current repository has an Android application and no iOS application tree.

Effect:
  Gate #97 does NOT wait for a hypothetical iOS app.

  iOS parity remains architecturally specified in this report but is not a V1
  gate until an iOS client becomes a supported release surface.

This is not an Android vendor lock-in:
  the Rust evidence model is platform-neutral;
  no Android service decides Mininet truth;
  other adapters can emit the same evidence type.

H97-02 — PHONE-INTEGRATED BLE/UWB/WI-FI RANGING ONLY.

Scope:
  BLE discovery/GATT;
  Bluetooth Channel Sounding where supported;
  UWB where supported;
  local Wi-Fi ranging where supported;
  software RTT fallback.

Out of scope:
  LoRa;
  RNode;
  packet radio;
  proprietary external radio accessories required for personhood.

The current invariant register explicitly says Radio/LoRa is not part of
Mininet.

H97-03 — CONNECTIVITY IS NOT PRESENCE.

A successful BLE link proves:
  devices exchanged bytes over a local bearer.

It does NOT prove:
  they are within the accepted physical-personhood distance.

A relay may be a perfectly valid network path and simultaneously be INVALID
presence evidence.

Code must keep those meanings separate.

H97-04 — USER-INITIATED FOREGROUND CEREMONIES ONLY.

Production personhood ranging is initiated by a visible user action.

No:
  continuous hidden personhood scanning;
  permanent background UWB;
  always-on background ranging;
  location-history harvesting.

Reason:
  privacy;
  battery;
  Android/iOS lifecycle constraints;
  no need to surveil a person's movements to prove one short encounter.

H97-05 — ANDROID 16 RANGINGMANAGER IS THE PRIMARY V1 ADAPTER.

On API 36+:
  use Android's unified `android.ranging.RangingManager`.

Capability preference:
  1. secure UWB;
  2. secure Bluetooth Channel Sounding;
  3. secure-capable Wi-Fi NAN RTT / 802.11az profile where peer support exists;
  4. other hardware ranging as Medium only if this gate certifies it;
  5. application software RTT fallback.

Why:
  Android 16 exposes one platform capability surface for:
    UWB;
    Bluetooth Channel Sounding;
    Wi-Fi NAN RTT;
    Bluetooth RSSI ranging.

The app already compiles/targets SDK 36.

H97-06 — ANDROID 14/15 UWB MAY USE THE JETPACK CORE UWB COMPATIBILITY PATH.

For supported UWB devices below API 36:
  AndroidX Core UWB may be used.

High assurance requires:
  provisioned STS;
  per-session key;
  secure OOB exchange;
  exact device profile passes this hardware campaign.

Static STS is NOT accepted for a high-assurance personhood presence profile.

H97-07 — SECURITY_LEVEL_SECURE IS REQUIRED WHERE ANDROID 16 OFFERS IT.

For Android 16 OOB ranging:
  request `SECURITY_LEVEL_SECURE`.

Source-derived mapping in current Android documentation:
  UWB -> Provisioned STS
  Bluetooth Channel Sounding -> security level four.

`SECURITY_LEVEL_BASIC` may be measured for diagnostics.

It may not be labeled `SecureHardware`.

H97-08 — BLE CHANNEL SOUNDING SECURITY LEVEL FOUR IS REQUIRED FOR ITS SECURE
PROFILE.

Security Level 4 provides the strongest Android-exposed CS security profile and
includes support for the Normalized Attack Detector Metric requirements.

For Bluetooth Channel Sounding:

  NADM:
    0x00 extremely unlikely
    0x01 very unlikely
    0x02 unlikely
  MAY be accepted by the policy.

  NADM:
    0x03 possible
    0x04 likely
    0x05 very likely
    0x06 extremely likely
  MUST reject the measurement/session for personhood.

  NADM:
    0xFF unknown
  MUST NOT qualify as `CertifiedSecure`.

It may be `CertifiedMedium` only if the rest of the hardware campaign supports
that profile.

H97-09 — UWB MUST USE PROVISIONED STS FOR SECURE CLASSIFICATION.

Android's current UWB guidance distinguishes:

  static STS:
    replay/relay susceptible;

  provisioned STS:
    replay/relay mitigated.

Therefore:
  static STS cannot earn `CertifiedSecure`.

This is necessary but NOT sufficient.

Published UWB research has demonstrated physical-layer distance-reduction
attacks against commercial IEEE 802.15.4z implementations even without knowing
cryptographic key material.

So Mininet never equates:
  "Provisioned STS" == "attack impossible."

H97-10 — NO VENDOR RADIO CLAIM IS SELF-AUTHORIZING.

A technology is promoted to a Mininet assurance class only by:

  exact configuration;
  exact OS/device capability;
  exact session binding;
  real calibration;
  real distance tests;
  relay/distance-reduction tests;
  reproducible evidence.

If a vendor says "secure" but the measurements fail:
  Mininet records the failure and downgrades the profile.

H97-11 — CURRENT `UwbRanging` IS TOO LOSSY FOR PRODUCTION.

It is superseded for production by:

  `RangingEvidenceV2`.

`UwbRanging` may remain for compatibility/tests until migration is complete.

H97-12 — PRESENCE QUALITY HAS FOUR EXPLICIT CLASSES.

  `WeakSoftware`
  `CertifiedMedium`
  `CertifiedSecure`
  `Unusable`

No bool named only:
  `hardware_ranged`
is sufficient for personhood policy.

H97-13 — SOFTWARE RTT IS A WEAK LOCALITY/FRESHNESS CHECK, NOT DISTANCE
BOUNDING.

Current default:
  max_rtt_ms = 50.

At speed of light, 50 ms is thousands of kilometers of round-trip propagation
budget before implementation/network overhead.

Therefore it cannot mean:
  "the peer is within two meters."

It helps reject:
  slow relays;
  stale/self-reported fabricated timing;
  grossly remote paths.

It does not defeat:
  fast LAN relay;
  dedicated wormhole;
  adversary close to both victims.

H97-14 — RSSI NEVER QUALIFIES AS PHYSICAL DISTANCE SECURITY.

BLE RSSI may be retained as:
  UX hint;
  debugging signal;
  gross vicinity hint.

It may not independently:
  accept a presence ceremony;
  increase personhood score;
  upgrade assurance.

H97-15 — 2.0 METERS IS THE V1 SECURE-PRESENCE DISTANCE THRESHOLD.

The application aims to prove:
  a deliberate near-person encounter.

V1 acceptance boundary:
  median secure hardware distance <= 2.00 m.

Additional distribution rule:
  90th percentile <= 2.50 m.

The threshold is not derived from RSSI.

H97-16 — A PRESENCE CEREMONY USES A DISTRIBUTION, NOT ONE "BEST" DISTANCE.

Minimum high/medium hardware sample count:
  12 valid ranging measurements.

Minimum observation interval:
  1.5 seconds.

Maximum ceremony measurement interval:
  10 seconds before restart.

Hardware decision uses:
  median;
  p10;
  p90;
  spread;
  attack/security indicators.

Never accept on:
  minimum distance sample alone.

Reason:
  security failures often create spuriously early/short measurements.

H97-17 — SOFTWARE RTT REMAINS ADDITIVE.

Every accepted production presence ceremony still performs the existing active
encrypted software RTT exchange.

Minimum RTT samples:
  4.

Current default maximum:
  50 ms.

A tighter empirically supported Android BLE value may be adopted later.

A hardware distance result does not bypass the RTT/channel checks.

H97-18 — OOB RANGING CONFIGURATION IS EXCHANGED INSIDE THE EXISTING
AUTHENTICATED MININET CHANNEL.

Android and Apple ranging both require application-level out-of-band exchange.

Mininet already has an authenticated encrypted channel and channel binding.

Use it.

Do NOT create:
  public pairing server;
  central matchmaker;
  account server;
  vendor database.

H97-19 — SECRET RANGING MATERIAL IS FRESH PER SESSION.

If UWB provisioned STS requires a session key:

  generate the session key with the project-approved OS CSPRNG;

  never hard-code it;

  never derive it from a public identifier;

  never reuse it across ceremonies;

  exchange it only inside the authenticated encrypted Mininet OOB channel;

  zeroize it where practical after ranging completes.

Do NOT invent a new KDF from the Mininet transport secret unless that exporter
construction is reviewed under the cryptography gate.

Simple safe V1:
  random session key + encrypted OOB transport.

H97-20 — THE SIGNED PRESENCE TRANSCRIPT BINDS THE RANGING SESSION.

Both devices sign a digest including:

  presence protocol version;
  network ID;
  encrypted channel binding;
  both device DIDs;
  both KEL digests;
  both fresh presence nonces;
  ranging technology;
  security profile;
  role mapping;
  OOB public-configuration digest;
  opaque session identifier/digest;
  sample count;
  robust statistics;
  accepted assurance class;
  start/finish monotonic-duration data;
  software RTT statistics.

Secret session keys are NOT included.

H97-21 — ONE-SIDED PLATFORM MEASUREMENTS ARE EXPLICIT.

Android 16 documentation says:
  UWB can deliver ranging data to peer devices;
  other Ranging module technologies may deliver data only to the initiator.

Therefore `RangingEvidenceV2` names:

  observer role;
  whether measurement is one-sided or bilateral.

One-sided measurement does not masquerade as bilateral.

Both devices still co-sign the final transcript.

H97-22 — FILE 4 PERSONHOOD INTEGRATION IS DEFINED HERE.

The File 4 personhood report gave physical presence a maximum of 20 points.

For that report, "accepted presence endorsement" SHALL mean:

  a Gate #97 profile classified `CertifiedMedium` or `CertifiedSecure`.

`WeakSoftware`:
  earns zero canonical PersonhoodPolicyV1 presence points.

It may still:
  support UX;
  support a provisional local meeting record;
  be retained as a weak non-personhood signal.

This preserves weakest-device access because File 4 also defines a complete
non-TEE/non-UWB remote-friendly route through other evidence classes.

No special ranging hardware becomes mandatory for humanity.

H97-23 — PRESENCE REMAINS ADDITIVE PERSONHOOD EVIDENCE.

Even `CertifiedSecure` means only:

  the tested radio/profile supplied strong evidence that the two participating
  devices were near during that session.

It does NOT prove:
  each device belongs to exactly one biological human;
  witness honesty;
  no secret was shared;
  global uniqueness.

File 4's mature-human vouch/time/multi-class requirements remain load-bearing.

H97-24 — PRODUCTION BUILDS CANNOT ACCEPT `TransportKind::InProcess`.

`InProcess` is CI-only.

Production `verify_presence` must fail if a wire/object from an untrusted peer
claims InProcess.

Implementation choices:
  compile-gate the variant from production wire format; or
  reject it when `PresencePolicyV2.production == true`.

Preferred:
  it never has a production wire tag.

H97-25 — PRODUCTION PRESENCE POLICY IS VERSIONED AND CAN BE STRICTER LOCALLY,
NEVER WEAKER.

Current `RangePolicy` is a caller-supplied struct.

For security-bearing personhood evidence:
  use canonical `PresencePolicyV2`.

A client may choose:
  shorter max distance;
  more samples;
  stricter NADM.

It may not submit a proof under weaker values and still call it canonical
personhood presence.

H97-26 — ANDROID RADIO PERMISSIONS ARE MINIMAL AND FEATURE-SCOPED.

For Android 12+ BLE:
  BLUETOOTH_SCAN;
  BLUETOOTH_ADVERTISE where peripheral role needed;
  BLUETOOTH_CONNECT.

For Android 16 unified ranging:
  android.permission.RANGING.

Do not request fine geographic location on API 31+ solely for BLE discovery if
Mininet does not derive geographic location from scan results.

`neverForLocation` is appropriate for BLE service discovery only.

The ranging API itself expresses proximity through its dedicated permission.

H97-27 — PERSONHOOD RANGING NEVER REQUIRES BACKGROUND LOCATION.

No `ACCESS_BACKGROUND_LOCATION` for Gate #97 presence.

If a future feature wants background ranging:
  that is a different privacy review.

H97-28 — FALLBACK MUST FAIL OPEN FOR NETWORK USE, FAIL CLOSED FOR PRESENCE
QUALITY.

If UWB/CS is unavailable:
  ordinary Mininet networking continues.

If secure ranging fails:
  the app may offer:
    retry;
    another certified ranging technology;
    non-presence personhood path.

It may NOT silently relabel software RTT as secure hardware evidence.

H97-29 — BLUETOOTH MESH RELAY AND PRESENCE ARE SEPARATE STATE MACHINES.

PR #333's multi-hop BLE work may become a useful connectivity substrate.

Presence ranging MUST be direct with the selected peer/profile.

A multi-hop route:
  may carry OOB/setup messages if the protocol explicitly binds the intended
  endpoint and the ranging framework still ranges the physical endpoint;

  may NOT count hop proximity as endpoint proximity.

H97-30 — NO CENTRAL DISCOVERY OR ALLOWLIST IS INTRODUCED TO MAKE TESTS PASS.

Nearby discovery:
  local BLE / local mechanisms.

Peer authenticity:
  Mininet channel + did:mini/KEL.

No:
  Mininet account login;
  server-issued pairing token;
  vendor allowlist of humans;
  hosted proximity oracle.

H97-31 — NO CONTINUOUS DEVICE IDENTIFIER ENTERS CANONICAL PERSONHOOD STATE.

5. EXTERNAL HARDWARE / SECURITY RESEARCH — WHAT IT CHANGES
======================================================================

This section is outside research used to select the production approach.

5.1 Android 16 unified Ranging module

Current Android documentation states that Android 16 adds a unified Ranging
module supporting:

  UWB;
  Bluetooth Channel Sounding;
  Wi-Fi NAN RTT;
  Bluetooth RSSI ranging.

It exposes:
  capabilities;
  availability;
  initiator/responder roles;
  ranging preferences;
  RANGING permission.

It requires an out-of-band peer/configuration exchange before ranging.

Mininet consequence:
  do not build four unrelated Android security stacks where the platform now
  provides one capability surface.

Use RangingManager as the primary API36 adapter.

5.2 Android security levels

Android 16 OOB ranging exposes:
  SECURITY_LEVEL_BASIC
  SECURITY_LEVEL_SECURE.

Android's documented secure examples map:
  UWB -> Provisioned STS;
  BLE Channel Sounding -> Security Level 4.

Mininet consequence:
  secure class requires SECURE, not BASIC.

5.3 Android UWB provisioned STS

Android's UWB guidance says:
  UWB peers exchange parameters through a secure OOB mechanism;
  parameters include a session key;
  provisioned STS is more secure than static STS;
  static STS is susceptible to replay/relay;
  provisioned STS mitigates that threat category.

Mininet consequence:
  OOB material rides the existing Mininet authenticated encrypted channel.

  Provisioned STS is mandatory for the secure UWB profile.

5.4 Android UWB calibration baseline

Android Open Source Project presence calibration currently requires at 1 m
line-of-sight:

  1000 measurements;

  95% accuracy expectation around +/-15 cm;

  test implementation:
    97.5th percentile - 2.5th percentile <30 cm;
    median in [0.75 m, 1.25 m].

Mininet adopts that test unchanged as a minimum UWB calibration floor.

A device pair that cannot meet the platform's own calibration expectation
cannot be Mininet CertifiedSecure.

5.5 Bluetooth Channel Sounding

Bluetooth SIG documentation describes Channel Sounding as combining:

  phase-based ranging for fine distance;
  secure RTT distance bounding;
  attack-detection features.

Bluetooth 6 defines a Normalized Attack Detector Metric (NADM).

Android exposes Channel Sounding Security Level 4 with:
  10 ns CS RTT accuracy;
  CS tones;
  sounding/random sequence payloads;
  NADM requirements.

Mininet consequence:
  use strongest profile;
  consume attack indicator;
  never ignore "possible/likely" attack status.

5.6 RSSI

Bluetooth and Mininet's own specification both treat RSSI as weaker than real
ranging.

RSSI changes with:
  body position;
  antenna orientation;
  walls;
  multipath;
  transmit power;
  adversarial amplification.

Mininet consequence:
  zero canonical personhood distance authority.

5.7 UWB is not automatically secure because the acronym says UWB

USENIX Security 2022 "Ghost Peak" demonstrated practical over-the-air distance
reduction against commercial 802.15.4z HRP UWB, including Apple U1 and
interoperability with NXP/Qorvo chips.

Published result:
  actual 12 m could be spoofed to 0 m;
  attack success up to 4%;
  no cryptographic material knowledge;
  inexpensive off-the-shelf attack hardware.

USENIX Security 2023 "Time for Change" demonstrated clock-based attacks on
commercial UWB and distance reductions from 10 m to 0 m.

Mininet consequence:
  never use a single UWB distance sample;
  do not equate STS with infallibility;
  test the actual deployment;
  preserve an explicit residual.

5.8 Secure UWB can be hardened

IEEE S&P 2024 work on secure ranging with 802.15.4z STS shows that STS can
enable secure ranging with an adequate receiver design.

USENIX Security 2024 PURE shows that a carefully composed UWB protocol can
achieve sub-meter relay protection against known physical-layer attacks on
modern smartphones with small overhead.

Mininet consequence:
  the radio primitive is not hopeless.

  Security is a property of:
    waveform/security mode;
    receiver;
    protocol;
    application binding;
    implementation;
    empirical validation.

5.9 Apple Nearby Interaction

Apple documents Nearby Interaction as:
  UWB-based distance/direction on supported devices;
  session-specific temporary discovery tokens;
  application-chosen peer discovery/data transport;
  foreground ranging;
  limited background behavior.

Mininet consequence:
  future iOS adapter can exchange the temporary discovery token over a Mininet
  authenticated local bearer and remain server-independent.

5.10 Android permissions / privacy

Current Android guidance for target Android 12+ uses:
  BLUETOOTH_SCAN;
  BLUETOOTH_ADVERTISE;
  BLUETOOTH_CONNECT.

If scan results are not used to derive geographic location, Android permits
the application to assert `neverForLocation`.

Android 16 unified ranging uses:
  RANGING.

Mininet consequence:
  ask only for the radio permissions the user deliberately invokes.

  Do not turn presence into geographic surveillance.

5.11 Android background limitations strengthen the foreground decision

Android says non-UWB ranging technologies cannot generally be used by
third-party apps for background ranging, and the OS may restrict ranging for:
  battery;
  performance;
  memory;
  concurrency.

Mininet does not need background personhood ranging.

Foreground ceremonies are:
  more predictable;
  more privacy-preserving;
  easier to test;
  less battery-hungry.

6. RANGING EVIDENCE V2 — REQUIRED DATA MODEL
======================================================================

Replace the production meaning of `UwbRanging` with a versioned structure.

Suggested Rust shape:

  enum RangingTechnologyV2 {
      Uwb,
      BluetoothChannelSounding,
      WifiNanRtt,
      SoftwareActiveRtt,
      BleRssiHint,
  }

  enum RangingSecurityProfileV2 {
      UwbProvisionedSts,
      UwbStaticSts,
      BleCsLevel4,
      BleCsLower,
      Wifi80211azSecured,
      PlatformUnspecified,
      SoftwareOnly,
  }

  enum MeasurementSidedness {
      InitiatorOnly,
      Bilateral,
  }

  enum AttackIndicatorV2 {
      NotAvailable,
      ExtremelyUnlikely,
      VeryUnlikely,
      Unlikely,
      Possible,
      Likely,
      VeryLikely,
      ExtremelyLikely,
      Unknown,
  }

  enum PresenceAssuranceV2 {
      WeakSoftware,
      CertifiedMedium,
      CertifiedSecure,
      Unusable,
  }

  struct RangingEvidenceV2 {
      version: u8,
      technology: RangingTechnologyV2,
      security_profile: RangingSecurityProfileV2,
      observer_role: RangingRole,
      sidedness: MeasurementSidedness,
      oob_config_digest: [u8; 32],
      session_binding_digest: [u8; 32],
      sample_count: u16,
      duration_ms: u32,
      median_distance_mm: u32,
      p10_distance_mm: u32,
      p90_distance_mm: u32,
      min_distance_mm: u32,
      max_distance_mm: u32,
      attack_indicator: AttackIndicatorV2,
      platform_quality_flags: u32,
      certified_assurance: PresenceAssuranceV2,
  }

Wire values:
  fixed-width where practical;
  versioned;
  bounded;
  canonical;
  unknown mandatory enum value -> reject.

Do not serialize:
  session secret;
  permanent radio address;
  raw scan list;
  GPS;
  IMEI;
  platform account ID.

6.1 Why median and tails

Distance-reduction attacks target unusually short observations.

Using:
  `min(distance)`
would select the attacker's favorite outlier.

Use:
  median as the primary threshold;
  p10/p90/spread as consistency checks.

6.2 Why the technology is explicit

A value of:
  120 cm

means radically different things if it came from:
  RSSI inference;
  application RTT;
  Wi-Fi RTT;
  P-STS UWB;
  Bluetooth CS Level 4.

The signed object must preserve that fact.

6.3 Why session binding is explicit

An attacker must not be able to:
  take a good range measurement from ceremony X;
  attach it to identities/nonces from ceremony Y.

The evidence needs a digest of the OOB/ranging session that is itself bound to
the same Mininet presence channel.

6.4 Why `certified_assurance` cannot be a free caller field

It is DERIVED by canonical policy.

The caller may supply raw technology/security/measurement fields.

Verifier computes the assurance class.

A malicious client does not get to send:
  `CertifiedSecure = true`.

6.5 Current v1 migration

During development:
  accept v1 only as WeakSoftware/test compatibility.

For personhood:
  V1 `UwbRanging` never upgrades itself to CertifiedMedium/Secure.

A deliberate migration transaction/object version is required.

7. CANONICAL PRESENCE POLICY V2
======================================================================

PresencePolicyV2 is the security-bearing policy for a personhood-eligible
presence event.

V2 launch constants:

  MAX_SECURE_DISTANCE_MM            = 2_000
  MAX_P90_DISTANCE_MM               = 2_500
  MIN_HARDWARE_SAMPLES              = 12
  MIN_HARDWARE_WINDOW_MS            = 1_500
  MAX_HARDWARE_WINDOW_MS            = 10_000

  MIN_SOFTWARE_RTT_SAMPLES          = 4
  MAX_SOFTWARE_RTT_MS               = 50

  MAX_SESSION_MS                    = 30_000
  MAX_CLOCK_SKEW_MS                 = 120_000
  MAX_ATTESTATION_AGE_MS            = 86_400_000

  SECURE_NADM_MAX                   = "unlikely" / 0x02

  REQUIRED_MUTUAL_SIGNATURES        = 2
  REQUIRED_DISTINCT_ROOTS           = 2

The personhood protocol may require stricter freshness than one day when
submitting an endorsement.

The local presence verifier may be stricter.

It may not be weaker and still produce a V2 personhood-eligible verdict.

7.1 Secure candidate

A session is a `SecureCandidate` only if ALL hold:

  technology is one of the approved secure-capable profiles;

  platform reports the expected security configuration;

  exact platform/device profile is covered by a current Gate #97 hardware
  evidence report;

  OOB setup is channel-bound;

  secret session material is fresh;

  minimum sample count/time satisfied;

  median <=2.00 m;

  p90 <=2.50 m;

  no attack indicator exceeds allowed value;

  software RTT passes;

  mutual signatures/delegation/replay checks pass.

Then the certified-profile registry determines:
  CertifiedSecure
or:
  CertifiedMedium.

7.2 CertifiedSecure

Requires the profile's HARDWARE CAMPAIGN to pass:

  calibration;
  honest near/far separation;
  obstruction/body tests;
  interference;
  lifecycle;
  replay;
  accessible relay;
  physical-layer attack campaign appropriate to the technology;
  privacy;
  battery/performance.

For the defined severe relay/distance-reduction campaign:
  >=3,000 attack attempts for each security technology family used as Secure
  in the launch profile;

  actual endpoint separation >=10 m;

  claimed/accepted threshold <=2 m;

  ZERO accepted `CertifiedSecure` presence verdicts.

Why 3,000:
  with zero observed successes, the simple rule-of-three 95% upper confidence
  bound is approximately 0.1%.

This is not a theorem of zero future attacks.

It is an empirical release floor.

7.3 CertifiedMedium

A profile may be CertifiedMedium if:

  real hardware ranging exists;
  secure OOB/session binding exists;
  sample distribution is validated;
  honest distance classification passes;
  lifecycle/privacy tests pass;
  accessible relay attacks pass;
  but:
    the strongest physical-layer attack campaign is unavailable, incomplete,
    or has a nonzero result below the explicit Medium ceiling.

Medium severe-attack observed false-accept ceiling:
  <=1.0% over >=1,000 adversarial attempts.

Any known deterministic/easy attack that crosses the 2 m boundary:
  profile is not Medium.

7.4 WeakSoftware

Includes:
  application RTT only;
  RSSI-only ranging;
  uncertified hardware number;
  static-STS UWB;
  BLE CS lower security profile without separate certification;
  unknown security profile;
  missing session binding;
  insufficient samples.

WeakSoftware:
  can produce a local meeting record;
  cannot contribute canonical physical-presence points to File 4 V1.

7.5 Unusable

Any profile with:
  repeated crashes;
  dangerous permission behavior;
  unacceptable false near/far classification;
  unstable session state;
  non-deterministic security profile reporting;
  easy relay acceptance;
  privacy violation;
  resource exhaustion;
  broken OOB binding
is Unusable for personhood.

Networking may still use the bearer independently.

8. ANDROID IMPLEMENTATION PROFILE
======================================================================

8.1 Android 16+ primary path

Add platform component:

  `AndroidRangingSourceV2`

Responsibilities:

  query `RangingManager`;
  capture capability snapshot;
  select highest approved mutually supported technology;
  build secure OOB config;
  exchange config through Mininet encrypted channel;
  start initiator/responder session;
  collect bounded measurements;
  collect security/attack indicators where exposed;
  compute raw observation summary;
  return platform-neutral `RangingObservationV2`.

It MUST NOT decide:
  personhood score;
  vote eligibility;
  human-share eligibility.

Rust/canonical policy derives final assurance.

8.2 Technology selection order

Default preference:

  1. UWB with provisioned STS / Android secure profile;
  2. Bluetooth Channel Sounding security level four;
  3. secure-capable Wi-Fi NAN RTT/802.11az profile;
  4. certified Medium hardware profile;
  5. software active RTT fallback.

Reason for UWB first:
  mature installed hardware and direct distance measurement.

Reason Bluetooth CS is still first-class:
  it can provide precision and secure RTT without an additional UWB radio on
  new hardware.

This order is not a political/vendor priority.
It is an assurance/capability preference.

The device pair must agree on the selected technology.

8.3 Capability negotiation

Each side sends, over the Mininet encrypted OOB channel:

  protocol version;
  supported ranging technology IDs;
  supported security profile IDs;
  role capabilities;
  maximum sample rate/measurement count if exposed;
  random session nonce;
  platform adapter version.

Negotiation selects:
  strongest intersection.

Downgrade resistance:
  both sides sign/bind the offered capability lists and selected profile in the
  final presence transcript.

An active attacker must not be able to strip:
  Secure UWB
and force:
  RSSI
without that downgrade becoming visible.

8.4 Ranging secret

For provisioned STS or other explicit session secret:

  generate independently with CSPRNG;

  exchange only after authenticated Mininet channel establishment;

  include only a hash/context commitment in the transcript;

  destroy local byte array as soon as platform session no longer needs it.

If platform API copies the secret internally:
  document that lifecycle limitation.

8.5 Role selection

Deterministic V1 role rule:

  compare BLAKE3 hashes of:
    ("mininet/presence/ranging-role/v2",
     channel_binding,
     initiator_presence_nonce,
     responder_presence_nonce,
     each device DID canonical bytes).

Lower derived value:
  ranging initiator.

Other:
  responder.

Purpose:
  both sides can agree without central assignment.

Do not use:
  phone brand;
  wealth;
  founder status;
  IP address.

If a platform requires one side to be controller for capability reasons:
  role override is allowed only when both sides bind the override reason and
  selected roles in transcript.

8.6 Android permission flow

The app presents a dedicated:
  "Verify nearby presence"

action.

Before requesting permission:
  explain that Mininet is measuring relative distance to this selected peer,
  not collecting GPS history.

Request only:
  BLE Nearby Devices permissions needed for local bearer;
  RANGING on API36+;
  legacy UWB permission for the AndroidX path when platform requires it.

Do not ask for background location.

For Android <=30 BLE scan:
  operating-system legacy requirements may need location permission.

The UI must state:
  the OS requires it for Bluetooth scanning on that version;
  Mininet does not store GPS location from the permission.

A user who declines:
  keeps ordinary non-presence functions.

8.7 Foreground state

Start ranging only while:
  presence ceremony screen is foreground;
  both users have explicitly started/accepted.

On background:
  stop/cancel session;
  mark incomplete;
  do not emit accepted evidence.

On return:
  restart with fresh session material/nonces.

8.8 Process death

If process is killed mid-ceremony:
  old ceremony cannot resume as accepted.

New process:
  new session ID;
  new ranging secret;
  new active range challenge;
  new final signed transcript.

No half-finished measurement is cached as valid.

8.9 Radio toggle

If Bluetooth/UWB/ranging becomes unavailable:
  session fails visibly;
  resources close;
  no presence evidence emitted.

After user re-enables:
  new session starts fresh.

8.10 Timeout

Every:
  discovery;
  GATT connect;
  OOB exchange;
  ranging start;
  measurement window;
  signing step

has a bounded timeout.

No Binder callback thread blocks indefinitely.

No queue grows without bound.

8.11 Concurrency

One personhood ceremony per local personhood identity at a time.

Ordinary BLE mesh/network traffic may coexist only if:
  it cannot starve;
  reorder;
  or mix the ceremony's OOB/ranging context.

Prefer:
  dedicated logical channel/context.

8.12 Hardware availability

No UWB:
  try secure Bluetooth CS if present.

No CS:
  try certified Wi-Fi ranging if present.

No certified hardware:
  fallback WeakSoftware.

Do not fail the Mininet app.

Do not falsely upgrade the result.

  Android BluetoothDevice address.

10.11 Airplane mode acceptance

10.12 Internet isolation proof

  block internet at test network/firewall level in addition to UI toggles where

Capture:

The test must not accidentally succeed over:

11. SOFTWARE ACTIVE RTT — EXACT STATUS
======================================================================

11.1 PASS mechanism

Current `active_range`:
  generates unpredictable challenge;
  encrypts it;
  measures local monotonic elapsed time;
  checks exact echo;
  uses distinct AAD.

Keep it.

11.2 FAIL mechanism

Current 50 ms threshold cannot prove two-meter proximity.

Approximate vacuum propagation:

  c ~= 299,792,458 m/s.

For a pure propagation-only round trip:
  50 ms permits a one-way path length on the order of 7,500 km.

Real BLE/GATT delays dominate at local scale.

Therefore:
  application milliseconds are scheduling/network locality;
  not meter-scale time-of-flight.

11.3 V2 use

Software RTT is mandatory as:
  authenticated active freshness;
  gross-relay sanity check.

It is never:
  CertifiedMedium
  or
  CertifiedSecure
by itself.

11.4 Statistics

Current verifier uses:
  minimum RTT.

For software RTT:
  retain minimum <=50ms for compatibility;
  also record median and p90 in V2 diagnostics.

Do not use those RTT milliseconds as meters.

11.5 Relay test

Direct same-room:
  establish baseline distribution.

Relay:
  compare distribution.

A low-latency relay that still passes 50ms:
  is expected residual.

The test report must not describe this as a software RTT failure if the design
already classifies software RTT weak.

It is proof that the classification is honest.

23. PERFORMANCE / BATTERY ACCEPTANCE
======================================================================

Presence is occasional.

It must not need continuous scanning.

23.1 Ceremony latency

Honest supported secure pair, 0.5–1.5m:

  median end-to-end ceremony <=10 seconds.

  p95 <=20 seconds.

  hard timeout <=30 seconds.

Measurement portion:
  >=1.5 seconds;
  <=10 seconds.

23.2 Reliability

Supported Certified profile:

  >=95% of honest in-range ceremonies succeed within two attempts in ordinary
  foreground use across the principal matrix.

Any individual device profile <90%:
  cannot be marketed as supported without a model-specific warning/fix.

23.3 Memory

No unbounded queue.

Peak application memory increase during 100 repeated ceremonies:
  no monotonic leak trend.

Practical V1 leak threshold:
  after GC/settle, resident app memory after 100 cycles must be within 20 MiB
  of the post-warmup 10-cycle baseline, excluding documented OS Bluetooth
  process memory outside app.

If platform noise makes this measure unreliable:
  use Android profiler allocation/leak tooling and document method.

23.4 CPU / ANR

No Android Application Not Responding event.

No blocking Bluetooth/Ranging callback waits on UI main thread.

Main-thread blocked interval caused by ceremony code:
  <100 ms per discrete operation.

23.5 Battery

Test:
  matched device/settings;
  60-minute control;
  60-minute test containing 100 start/range/sign/close ceremonies or as many
  complete sequential cycles as the profile permits.

Target:
  additional battery consumption attributable to Mininet ceremony workload
  <=5 percentage points of full battery capacity versus matched control.

This is deliberately generous for a stress workload.

Normal user behavior is far lower.

Any thermal severe/throttle condition caused by the workload:
  investigate before certification.

23.6 Background

Zero personhood ranging sessions remain active five seconds after:
  ceremony cancel;
  app background;
  app force-stop callback/resource cleanup.

System-level unavoidable teardown delay must be measured and documented.

28. HARDWARE CLASSIFICATION ALGORITHM
======================================================================

Inputs:
  canonical PresencePolicyV2;
  RangingEvidenceV2;
  certified profile registry;
  signed presence envelope.

Pseudo-decision:

  if transport == InProcess in production:
      reject

  verify:
      version
      channel binding
      devices/KELs
      capabilities
      signatures
      nonces
      replay
      software active RTT

  if no RangingEvidenceV2:
      result = WeakSoftware

  else:
      verify evidence canonical bounds
      profile = registry.match(platform/security/technology)

      if profile absent:
          result = WeakSoftware

      if evidence.sample_count <12:
          result = WeakSoftware

      if evidence.duration_ms <1500 or >10000:
          result = WeakSoftware

      if evidence.median_distance_mm >2000:
          reject physical-presence acceptance

      if evidence.p90_distance_mm >2500:
          reject physical-presence acceptance

      if attack_indicator >=Possible:
          reject

      if attack_indicator ==Unknown and profile requires NADM:
          assurance <=CertifiedMedium

      verify OOB/session binding digest.

      result = min(profile.assurance, evidence_supported_assurance)

The resulting assurance:
  is deterministic;
  is not client-selected.

For File 4:
  only CertifiedMedium/Secure create a canonical accepted presence endorsement.
